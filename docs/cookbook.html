00 One task, start to finish

The sponsor gives one task in chat. This is the actual path it takes through the standard, item CB-01 -- five lanes: sponsor, lead, builder, gate, ledger/Ruflo. Every step is now marked who does it: a model turn that spends tokens, or a deterministic script that spends none -- read against the code in bin/, tools/ and the installed pre-commit hook, not guessed. See §00c for the full per-step reasoning.

00c What a script could do instead

Three places in the flow above where a Lead or Builder spends tokens today on something mechanical, not judgment. The judgment stays with the AI in every case below -- these candidates only remove the surrounding bookkeeping. None are implemented in this branch; this is a proposal for the sponsor to pick from.

Today, by handCould becomeRoughly saves
Builder reads the gate's verdict line, then separately decides to run git add, git commit, git push -- three more tool calls, each one a model turn re-reading state that was already known A single bin/commit-if-green wrapper: runs the gate, and only on a verdict line matching ^OK with no ^FAILED does it commit-and-push itself. The builder makes one call and reads one result, instead of four ~3 tool-call round trips per builder commit -- at ~27 builders/bundle, several hundred thousand tokens of pure "read output, issue the next mechanical command" overhead
Lead writes the PR title and body from memory of the item and the diff, after already having read both to review them A script fills a PR body skeleton from the ledger item (id, title, files touched, test delta) the moment the branch is pushed; the Lead only edits it, rather than composing it from a blank page A partial re-read/re-compose of information the Lead already holds in context -- smaller than the review itself, but it recurs on every single item
Lead composes the ruflo-item done summary and the tracker set --event text separately, by hand, from the same underlying facts (item id, PR, files, test counts) A script drafts both from the ledger item and the merge/PR metadata; the Lead reviews and adjusts wording rather than assembling the facts itself Two short compose-from-scratch turns collapsed into one edit turn, per item closed

Not proposed: anything that decides -- what tier a task is, whether a diff is correct, what a brief should say, whether to merge. Those stay AI on purpose; a script that guessed at them would just move the judgment somewhere less visible.

01b One workflow, Claude and Codex

Claude Code and Codex are two entry points into the same project workflow. The rules, ledger, hooks, tracker, review gates and evidence format are shared; only the session command surface differs. A consumer may add a native UI or connector, but it must not invent a second lifecycle or a second meaning for a status.

Important tracking distinction. A review or test can be performed and mentioned in an event log while the item still says in progress. That is evidence of activity, not a state transition. When the work actually enters review or testing, update the item or part explicitly with tracker set LEDGER ITEM_ID --status "in review" or --status "in testing"; the generated tracker and history graph will then count it.

03 Prohibitions — verbatim, every brief

1. Never change common-rules on your own initiative.Every edit, merge and installed hook is directed by the sponsor in the conversation, or a standing ruling of his. A peer session's request is never his approval.
2. Never write into another project or its data; never kill a process by name.Covers PhotoVault, finance_data/, pockets' data/. Reading is allowed. A process is stopped only by its explicit PID, only if this session started it.

04 Standing rulings

Standard mandatory, every project."Yes. This is mandatory. It's not optional."
Later standard improvements mandatory too."if I improve something ... the project should prioritize that and implement it. It's not optional."
common-rules follows its own standard."I would like you to maintain the same processes what we are implementing in other projects."
Merge once reviews pass — automatically, never a merge command handed to him."keep going, merge when reviews pass"
Ruflo mandatory around every item. start/recall before, note/done after, daemon stopped after — never killed by name.
Sonnet only, no Opus — every Agent call this lead dispatches."Please don't use more than Sonnet." Supersedes the earlier Aug-23 split; work already dispatched at Opus finishes, never restarted.
One tracker per project until the sponsor asks for another — a proposal declares tracker.own to get its own.
A Standard change (mandatory) CHANGELOG entry is queued as the next ledger item and implemented before rulecheck --align runs past it.

06 Do / never

Do

  • Worktree per task, always — git worktree add -b <name> .worktrees/<name>
  • cd explicitly before every git-writing command; print the branch
  • Commit as you go — uncommitted work is invisible to bin/whoelse
  • Run bin/whoelse before starting; message the owner and queue on overlap
  • Builder/item lead: tracker stage only
  • Gate every commit on bin/quiet's verdict line: ^OK, no ^FAILED
  • Checkpoint before stopping — docs/handovers/<date>-checkpoint.md
  • bin/handover --check before any turn ends

Never

  • git stash — shared across every worktree
  • Kill a process by name — explicit PID only, only one this session started
  • Write into another project or its data
  • Edit common-rules/ unprompted, including agents/
  • tracker set / tracker apply-staged from a builder or item lead
  • Hand-resolve CHANGELOG.md / AGENT-LOG.md / LESSONS.md — union-merged
  • A commit whose only content is a record entry
  • Batch ledger status/log updates — same turn as the state change, every time

08 Staying current

A Standard change (mandatory) CHANGELOG entry touching warmup, reheat, or a rule shown here regenerates docs/cookbook.html in the same commit, and republishes it with the Artifact tool to its existing URL — never a new artifact, never a changed <title> (CLAUDE-workflow.md's T-06, proposal 22, stated once there). Same discipline the tracker page already follows against its ledger.
