What was found

  • Established schemes keep value and effort apart. Story points measure effort only. WSJF divides value, time criticality and risk reduction by job size. RICE needs a user "reach" that internal items do not have. (Research report, 15 September 2026.)
  • AI-assigned story points are not reliable cold. Two 2026 studies (arXiv 2603.06276, 2604.03443) found zero-shot LLM estimates usable only relatively, with no significant gain from retrieval. The research agent could not confirm error sizes from the full texts.
  • Review depth by risk is the best-corroborated practice: change-advisory classes, risk-based testing, and an open review-tier proposal for agent workflows. This matches proposal 23, D2.
  • Clustering by file-path overlap is the cheapest signal and the same one used to class risk. Its known pitfall: unrelated items in one folder look alike.
  • When one agent both estimates and executes, points can drift toward whatever makes the work cheaper. Estimates must be checked against measured cost per item, and bin/spend can already measure that from transcripts.
  • Not verified: no source shows value-and-complexity routing in a production AI coding workflow; the scheme below is reasoning built on the sources, not copied practice.

Options

A · Value, points and risk, with a routing table

Each item carries value (high, medium, low; yours), points (1, 2, 3, 5, 8, 13; set by the lead or scout), risk (standard, elevated, restricted; from paths) and cluster (surface). A table turns them into review depth, effort and bundling. Models stay as they are (proposal 23, D8).

Costs: four ledger fields, a validator change, a routing table. Rules out: tiering by complexity alone.

B · WSJF ranking only

One score, (value + urgency + risk reduction) ÷ points, orders the whole queue; the top quarter gets the deeper treatment.

Costs: least. Rules out: separating "do this first" from "check this carefully": a low-score item can still touch money.

C · Risk class only, no points

Three risk classes decide review and checks; nobody estimates size.

Costs: least estimation. Rules out: seeing effort before work starts, and sizing bundles.

Recommended: A. It is the only option that keeps your two concerns, value and effort, visible and apart, while risk alone decides who checks the work.

Decisions

Each numbered line is one thing the sponsor answers. Keep the numbers stable once shown: answers and ledger items cite them.

  1. D1. Which scheme: A (value, points, risk, routing table), B (WSJF ranking only) or C (risk class only)?
  2. D2. Value: do you set a default per surface (for example the PhotoVault app high) and override single items, or set it on every item?
  3. D3. Points: should the agent that builds an item see its points, or are they set by the lead or scout and kept from the builder?
  4. D4. Is every common-rules change risk "restricted", or only changes that carry a Standard change line?
  5. D5. How often are points checked against measured cost per item: every 20 items, weekly, or monthly?
  6. D6. The catalogue: issues not taken now get a cluster by file-path overlap and appear on the project's tracker page; or GitHub labels only; or clustering by text similarity?
