A proposal declares the milestones it creates, and its status follows from them

proposeddesign-conceptProposal 16 · topic: proposal-milestone-pipeline

The sponsor's observation, 2026-08-20: "each proposal is a feature where all the decisions it needs to do in a pipeline are different milestones." Measured against the proposals that actually exist, that is true for one class of proposal and false for another — and the distinction is the whole value. Where it holds, it makes a proposal's status derivable instead of asserted, which closes a hole opened four days ago.

What this proposes An accepted proposal that authorises building declares the milestones it creates. Only its sequencing decisions become pipeline stages; the rest are parameters. Milestones may still arise with no proposal. And a proposal's terminal status — completed or completed in part — is then computed from its milestones' states rather than typed by hand, which makes the exceptions list write itself.

The observation holds, and here is the evidence three for three

Every accepted proposal that authorised building has produced an ordered chain, and its own decisions fixed the order:

ProposalThe decisions that set an orderBecame
24 · design system D2 tokens alone → D3 migrate page by page → D5 dark mode only after #580 → #532 → #531
23 · the work light D5 — the event-loop stalls land before the footer #537 → #536
25 · the feature book D3 — surfaces, then engines, then channels ten chapters, in that order

In each case the ordering was argued in the proposal and then obeyed by the work. Proposal 24's D5 is the clearest: dark mode last, because flipping it first would leave the literals unmigrated and the app would ship visibly seamed. That is a pipeline stage with a stated reason, and it is indistinguishable in kind from a milestone.

And it does not generalise two ways it breaks

Not every decision is a stage

Proposal 24's D6 — "keep the manual palette picker once the app follows the OS" — is a yes/no that changes what gets built, not when. Same for 23's D3 (failures stay until dismissed) and D4 (the tracked-scope test is a hard gate). These are parameters: recorded in the Decided block, consumed by whoever implements, never a row in a plan.

Rule of thumb: a decision becomes a milestone only if it answers "what must be true before the next thing starts". If it answers "what shape should this take", it is a parameter.

Not every proposal produces milestones

Proposal 22's D1 was "No new timing-test work. The audit is the deliverable." A research proposal whose honest conclusion is do not build this. It creates zero milestones, and no amount of waiting will change that. A rule that demanded milestones from every proposal would push that proposal to invent some.

An earlier draft of this paragraph said proposal 22 "is complete". It is not — it still reads proposed. The example survives the correction untouched, but the error is left recorded rather than quietly deleted, because it is this proposal's own thesis happening to this proposal: an asserted status went stale inside the document arguing that asserted statuses go stale. Found by the finance-tracker pilot, not by review.

Not every milestone comes from a proposal

finance-tracker's milestone 6 — "money figures survive negative cases on the real book" — came from a quality review, not a proposal. Requiring a proposal first would be ceremony charged against the most important row in that plan.

What it buys a hole opened on 2026-08-19, closed

Four days ago the shared rules gained completed and completed in part, the latter requiring a documented exceptions list — the sponsor's own words were that a binary done/not-done "is what makes people quietly mark things done".

That requirement currently depends on somebody remembering to enumerate what was skipped. Which is the same discipline problem, one level up.

If a proposal declares its milestones, its status stops being a claim every declared milestone done  →  completed
some done, some not  →  completed in part, and the exceptions list is the unfinished rows — it writes itself, and cannot be fudged by omission.

That is the strongest argument for the sponsor's idea, and it is not the one he made. He proposed the structure; this is what the structure pays for.

The caution why the link points one way

A proposal is a record; a milestone plan is alive

Proposals are the record of why a decision was made, and the shared rules already treat them as immutable once decided. The milestone plan is explicitly "a live document" that "moves when a state changes… or when the order changes because a proof came back badly".

Couple them tightly and one of two bad things happens: the plan freezes to keep the proposal true, or the proposal gets edited to match the plan — rewriting the record of a decision after the fact, which is the failure the whole numbering-and-status apparatus exists to prevent.

So the link is one-directional. A milestone row cites its originating proposal. A proposal lists the milestones it created at the moment it was accepted, and is never edited afterwards. If the plan later drops a milestone, that shows up as the proposal being completed in part — which is exactly the honest outcome, recorded rather than tidied away.

Where D5 lands measured after this proposal was written

The checker D5 asks for could not fire in the repo that ships it

D5's argument is that this repo has built three checkers that sat unconsumed, so a fourth should be wired into bin/land rather than left advisory. That argument is sound and the measurement below does not contradict it. It adds a fourth failure mode the first three do not cover.

Every gate in bin/land sits behind [ -f "$stamp_file" ] — the project's .common-rules-version. That is deliberate and right: a project that never ran rulecheck --align never claimed to be governed by these rules, so it is never refused on them. But common-rules does not adopt itself. It carries no stamp, so every gate skips here. It also has no CLAUDE-checklist.md at all: no feature register, no ## Milestones table, no docs/milestones.html.

So the repo that authors this proposal, hosts it, and would ship its checker is the one place the checker is structurally unable to run — and proposal 16 would be the first proposal here it could ever apply to.

The fourth failure mode is worse than the three D5 names, because it looks like a pass. rulecheck --quiet, proposalcheck and milestonecheck each failed by nobody calling them — visibly inert, and each needed a second change to give it teeth. A gate that is called and always skips reports success. Nothing prompts the second change, because nothing looks wrong.

This is not hypothetical here. proposalcheck reports of this repo today that "every proposal that asked decisions recorded them" — and that is vacuously true: not one of common-rules' sixteen proposals carries an <ol class="decisions"> list at all. Zero asked. The check has never once had anything to check, and its output has read as a pass throughout.

Two consequences worth carrying into D5, neither of which decides it:

  • A checker enforcing declared milestones needs to say which of "checked and clean" or "nothing to check" it means. The 0/1/2 convention proposalcheck and milestonecheck already share — where 2 is "could not check" — is the existing answer, and it exists precisely so a skip is not read as a pass.
  • Enforcement in bin/land reaches adopting projects only. If this rule is meant to bind the rules repo too, that is a second change — giving common-rules a checklist and a plan of its own — and it is a larger question than this proposal, which is why it is named here rather than folded into D5.

Measured 2026-08-20 against this repo, by the session handed proposal 16 to implement, while checking whether its claims held on a second corpus. The pilot in finance-tracker tests a different claim — whether decisions sort into stages and parameters — and its findings are still outstanding.

The cost case found 2026-08-23, in finance-tracker's own book

Everything above argues this proposal from tidiness — statuses that ought to be derivable, exceptions lists that ought to write themselves. Three days after it was written, an audit of finance-tracker's Spending area produced the argument from damage, which is the one it was missing.

Proposal 01, One book for the household, is stamped built. Its Workstream 3 says, verbatim:

"The single largest genuine gap: the app has no concept of income. Inflow categories (salary, interest, refund, FD maturity, transfer-in) and a transfer category on the expense side… On top of that, a savings rate, and the sentence you actually asked for, generated as a monthly household statement and archived."

The transfer half shipped, as flows.py. The income half never did. And because the proposal carries a terminal status, nothing has tracked the remainder since. CLAUDE-checklist.md admits this about itself, in its own words: "proposal 01's two orphans (the income model and the retirement half — neither is tracked anywhere since 01 was marked built)". A search of every issue in that repo for income, salary and savings rate returned nothing. The work was not deprioritised, argued down, or deferred. It was lost, by a status.

What surfaced it, and what did not Not a review, not a checker, not this proposal. The sponsor asked in August 2026 for a feature — total income, income by kind, a figure he could plan an investment against — and only then did anyone discover it had already been accepted, scoped in detail, and marked done. Between those two dates the ordinary machinery of the project ran continuously and reported nothing wrong, because by every record it consults, nothing was.

And the model as written would not have caught it either. That is the part worth stating against interest. This proposal derives completed and completed in part from milestone states. Proposal 01 is built — a status that asserts done-ness while sitting outside the derivation entirely. Proposal 01 also declares no milestones, so there is nothing to derive from; it is one of the thirty-eight the finance-tracker pilot found declaring none. Under this proposal's rules, unchanged, it computes to completed and stays exactly as wrong as it is today.

So the cost case is evidence for the proposal and a correction to it at the same time. It establishes that an asserted terminal status can lose real, accepted, scoped work for months — which is the strongest argument for derivation anyone has produced. It also establishes that derivation is worthless unless every status that reads as finished is derived, and unless a proposal declaring zero milestones is treated as unanswerable rather than as complete. Both gaps are put to the sponsor in D4 below rather than fixed here.

Filed as finance-tracker issue #624 so the capability is tracked whatever is decided about this proposal — the immediate harm is repaired independently of the rule. The Spending audit of 2026-08-23 also found the milestone row, the feature register and the closed issue #254 disagreeing with each other about that feature's state, which is the same class of defect one level down.

Decisions needed nothing is built until these are answered

  1. D1 — Adopt the link at all. An accepted proposal that authorises building declares the milestones it creates; a milestone row cites its proposal where it has one. Recommended yes: it is the prerequisite for everything below.
  2. D2 — Only sequencing decisions become milestones. Parameters stay parameters. Recommended yes — the alternative turns every yes/no into a plan row and the plan stops being readable.
  3. D3 — Milestones may exist with no proposal. Recommended yes. Requiring one would have charged ceremony against finance-tracker's money-correctness milestone, which came from a review.
  4. D4 — Terminal status is computed, not typed. All declared milestones done → completed; some → completed in part with the unfinished rows as the exceptions list. Recommended yes — this is the payoff, and it removes a discipline dependency.

    Two gaps the cost case exposed, both of which D4 must answer or it does not work. (a) built reads as finished but sits outside the derivation — and built is the status that lost proposal 01's income model. Every status that reads as finished must be derived, or the rule simply moves the hiding place. (b) A proposal declaring zero milestones currently computes to completed, since vacuously all of none are done. That is the same vacuous pass measured in Where D5 lands, arriving through the status rule instead of the checker, and it is the state of every one of finance-tracker's thirty-eight proposals today. Zero declared milestones must compute to unanswerable — a proposal that never said what it would produce cannot have its completion derived, and should say so rather than claim success. Recommended: derive over the full terminal vocabulary, and treat an empty declaration as unanswerable rather than complete.

  5. D5 — Is it enforced? A checker could verify that every completed proposal's declared milestones are all done. Recommended yes, and wired into bin/land rather than left advisory: this repo has now built three checkers that sat unconsumed (rulecheck --quiet, proposalcheck, milestonecheck) and each needed a second change to give it teeth. See Where D5 lands above: in this repo such a checker would be called and would always skip, which is a fourth failure mode that reads as a pass. That does not change what D5 asks, but it changes what answering yes has to account for.
  6. D6 — Retrofit, or new proposals only? Recommended new only, with the same date-floor mechanism the decisions rule already uses. finance-tracker has eight accepted proposals whose milestones were never declared and cannot be reconstructed honestly.
