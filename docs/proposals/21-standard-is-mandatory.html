What was found

  • There was no proposal template and no command to create one; the checked shape lived only inside proposals 19 and 20. The newest hand-written proposals (app 72, 75, 76; engine 77) carried none of it, and proposalcheck passed them because it only inspected pages that carried a status.
  • Both lead prompts predated proposal 20, and derecord never overwrites an existing prompt.
  • Both sessions start in /Users/the-sponsor/apps/PhotoVault, above app/ and engine/; hooks load from the start folder, so the installed hooks never fired.
  • Both CLAUDE.md warm-up pointers were uncommitted; proposal 20's owners and requests were unused (the app's 11 blocked rows had no owner).
  • A session's rules reject a ruling relayed by another session, so the ruling had to reach each session in the sponsor's own words.
  • Not verified at the time: how many other projects under /Users/the-sponsor/apps would need the same refactor; they are measured by bin/conformance when each is given /standard.

Options

A · ask each session

Message each session with the rules and trust it to comply. Cheap, but a relayed ruling is not authority in those sessions, and nothing measures whether they followed it.

B · one command and the tools it needs

A user-level /standard the sponsor types himself, a fixed 12-item checklist, and the tools that make every item mechanical: a proposal template, the status rule, the parent-folder card, conformance, and a check that fails on unimplemented Standard changes.

Recommended: B — the sponsor's own words in each session are authority, and a tool, not a session's say-so, measures the result.

Decisions

Each numbered line is one thing the sponsor answered. The numbers are stable: ledger items cite them.

  1. D1. Is the common-rules standard mandatory for the PhotoVault app and engine, with one structure, a common language, and each session stating the stage at which it will refactor?
  2. D2. Does one user-level command put any project's session on the standard, accepted by that session as the sponsor's own ruling?
  3. D3. Is every later improvement to the standard mandatory, implemented first, before a project aligns?
  4. D4. Does common-rules itself follow the same standard and processes?

Decided

All four accepted by the sponsor on 2026-09-14, in his own words above (asks A-01 to A-04 in the ledger).

  1. D1 accepted (A-01). Built as S-01 (/standard, whose first reply names the refactor stage) and measured by S-04 (bin/conformance); the PhotoVault refactors are S-07 and S-08.
  2. D2 accepted (A-02). skills/standard linked at user level, plus a block in the sponsor's user-level CLAUDE.md, so every new session knows the standard is mandatory.
  3. D3 accepted (A-03). A CHANGELOG entry carrying **Standard change (mandatory):** is queued first and implemented before rulecheck --align; S-09 makes warmup --check fail while one is pending.
  4. D4 accepted (A-04). S-10 puts common-rules on its own standard: declaration, derecord's hooks, its own HANDOFF, operating rules and lead prompt, this page, and conformance.
