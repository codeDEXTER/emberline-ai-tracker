33 · proposed · Why the standard gets missed, and what to cut

Proposal 33 · proposed 2026-09-18. Twenty-one findings in one session, a release that had to be cut twice because main went red, and a rule the briefs themselves broke ten times. This is the review of why, measured rather than argued, and the five things that would change it. The cutting decisions are the sponsor's.

The ask

Can you do a thorough review and identify why we are missing these items? Can we optimize all these rules so when I warm up or reheat a project, they follow it to the point and not miss anything? Do we need to deprecate any of the old mechanisms and make it as concise and precise as possible? The sponsor, 18 Sep 2026, in this session's chat; recorded as ask A-01 in the ledger beside this page.

What was found

  • Nine of sixteen. Of the 126 done-criteria across these ledgers, 16 demand a measurement — and nine of those sixteen were closed without performing it (finding 23/F-02: H-02, H-03, Z-05, M-03, L-01, L-02, L-06, L-07, T-06). The build half was done in every case. The verification half was skipped and the item closed anyway. Nothing refuses. 23/F-07 and 28/F-01 are two more of the same shape, found separately.
  • Checks that fire at the wrong moment. docs/workflow.html drifted behind the rules twice in two days and main went red both times. The check that catches it — bin/workflow-stamp --check — exists and is correct, and it lives in gates.merge, while a builder runs a scoped test set. So it only ever fires at integration, when the cost is highest and the author has moved on.
  • Copies that drift in silence. .claude/skills/{warmup,reheat}/SKILL.md are committed copies derecord keeps identical to the source — but only when someone runs derecord. They sat two days stale, missing the very fixes shipped that morning, and Claude Code prefers those directory-scoped copies for files under that directory (31/F-07).
  • 76 prose rules against 12 machine checks, and a mandatory read of about 16,200 tokens — 13% of a context window before any work begins. CLAUDE-workflow.md alone is 10,100 of it.
  • What held was code; what failed was prose. Held: parts validation, quiet's verdict read from the runner's own summary, land's refusals, proposalcheck. Failed: "use the existing tool, not an inline copy" is measurably failing at 9.54 cat/sed -n calls per 100 tool calls against the 6.40 that would count as halved — and it moved backwards since the interim reading. "The ledger has one writer; a builder stages, never sets" was broken ten times in one day by the lead's own brief template (31/F-06).
  • Tool defects surface on first real use, not in tests. Seven of the twenty-one findings are that shape: ruflo-item failing in every worktree, spend calibrate --help running a real calibration, --add-part unable to build parts up, --waiting-until silently ignored when editing, rulecheck --align stamping unconditionally, land_one trusting an exit code.
  • Not verified: whether the same ratio holds outside this repo. Every number here is common-rules' own ledgers and transcripts; no project has enough closed items under the standard to compare against.

Options

A · Write the rules better

Rewrite the prose so it is shorter, sharper and harder to skim past. Cheap, and it is what every previous round did — the must-read has a 3,000-word target and stands at 8,600. The evidence says a session that must remember 76 rules will follow the ones it happens to recall.

B · Make the machine refuse

Convert rules into refusals wherever a refusal is possible, move the checks earlier so they fire on the author's own machine, and cut whatever is left that nothing enforces. Costs real work per rule, and some rules — judgment ones — cannot become code and must stay prose, deliberately and few.

Recommended: B, and the reason is in the evidence above. Every rule that held this session was enforced by code. Every rule that failed was prose asking a session to remember. A shorter document is still a document.

Decisions

Each numbered line is one thing the sponsor answers. Keep the numbers stable once shown: answers and ledger items cite them.

  1. D1. Should closing an item be refused when its own done criterion demands a measurement and the closing event carries no number? → R-01
  2. D2. Should the cheap pre-checks move into the builder's own gate, so drift fails on the author's machine rather than at integration? → R-02
  3. D3. Should conformance fail a project whose skill copies have drifted from the source? → R-03
  4. D4. Every rule in the must-read gets one of three verdicts — enforced by code, moved to reference and out of the mandatory read, or cut. Is that inventory worth doing, knowing it will shrink what a session is told? → R-04
  5. D5. What may be deleted outright: /standard (its own description says it is a shortcut for /warmup and will be removed), the folded Lanes block, and tracker set --add-part's incremental path that cannot work. Deprecations that never delete are how a standard grows past being read. → R-05

Decided

Not decided yet. D4 and D5 delete things a session currently reads, and that is the sponsor's call rather than the lead's. D1 to D3 add refusals and cost nothing but the work.
