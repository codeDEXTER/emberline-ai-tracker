27 · proposed · Time and tokens per task, in one place

Proposal 27 · proposed 2026-09-15. Every session's transcripts already record tokens and timestamps. This proposal collects them, without anyone typing anything, into one database for all projects, tied to ledger items, and shows an end-of-day review of time and tokens per task, session and project.

The ask

Second thing, uh, it needs to be a low effort uh, thing that all the tasks and everything should be tracked, time and tokens. So at the end of the day, we can, you know, continuously review these things across different sessions. There could be a central database maintained for all sessions and everything, and we updated their regularly. The sponsor, 15 September 2026, in the Common Rules rework session; proposal 27 ask A-01.

What was found

  • Partly implemented. bin/spend reads the transcripts and reports output tokens per task (report) and per day across projects (today). It keeps no database and recomputes on every run.
  • It misses all subagent spend: it reads ~/.agent-data/projects/*/*.jsonl only, while agents write to <session>/subagents/*.jsonl. On 15 September it reported 100% management and 0 worktree tokens.
  • It overcounts: it adds the usage of every streamed record, and a response is written about 3.6 times (4,818 records for 1,322 messages in the PhotoVault App lead). It counts output tokens only, so cache reads, 68–79% of lead spend, are invisible.
  • It cannot say which item work was for: a task is a worktree name, and agent worktrees are named agent-<id>. It records no time.
  • bin/tower shows cost by week and notes that 96.8% of tokens sit in the (main checkout) and (management) pseudo-tasks.
  • Not verified: how long a first full collection of every transcript takes (tower measured 26.8 s for its cost pass).

Options

A · Collector into one SQLite database

bin/worklog collect reads new transcript lines since its last run (lead and subagents), counts each response once, and stores per request: project, session, agent, model, item id, all four token kinds, list-price cost and timestamps. A Stop hook runs it after each session turn; a nightly run catches the rest. bin/worklog day writes the evening review page. The database lives outside every repository.

B · Daily JSON files

The same collector writes one JSON-lines file per day instead of a database. Costs: less machinery. Rules out: fast queries across weeks and sessions.

C · Fix bin/spend only

Add subagents, count each response once, add all token kinds and time; keep recomputing each run. Costs: least. Rules out: history that survives transcript clean-up, and a central record.

Recommended: A. It is the only option that keeps a central record, needs no typing, and can join tokens and time to ledger items across every session.

Decisions

Each numbered line is one thing the sponsor answers. Keep the numbers stable once shown: answers and ledger items cite them.

  1. D1. Storage: A (one SQLite database), B (daily JSON files) or C (fix bin/spend only)?
  2. D2. When it updates: after each session turn plus nightly, nightly only, or only when asked?
  3. D3. How work is tied to a task: brief tag, then branch, then session; or worktree name only?
  4. D4. Time: active time (gaps over 5 minutes left out) or first-to-last wall clock?
  5. D5. The daily review: an evening page and a line on the /warmup card, the page only, or the card line only?
  6. D6. Fix bin/spend's subagent and double-counting gaps first, or replace bin/spend with the collector?
