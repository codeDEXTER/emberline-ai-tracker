How it's decided

completion % sum of the done parts' shares. Nothing else moves the number.
finish now under 80% done, or any open part is high risk.
back burner 80% or more done, and what's left is low or medium risk.
waiting owned by another project, or waiting for a date.
risk shown as a word only — high, medium or low — with the reason on hover, never a number.

What was found

  • Lanes (tools/tracker/lanes.py) sorts by share = value weight × points / queue total and cuts at 80% cumulative share into "Now", then sorts the tail by risk = impact × likelihood. Neither number is completion of anything — a small, unstarted item can outrank a mostly-done one, which is what read as "17%" with no formula behind it.
  • common-rules declares risk_always: "restricted" in .common-rules.json, and lanes.py forces every restricted item's risk to 9 and marks it "alone". Every item in this project reads risk 9 today — the risk column is uninformative here by construction.
  • No item in any of the 10 ledgers has sub-parts today. "L-02.A, B, C" (the sponsor's own example) does not exist yet — it names the convention this proposal builds.
  • Measured against the current ledgers (99 real items, Q-03 excluded — a queue row this same warm-up run added and then reverted, not counted): 94 done, 5 open (W-10, L-07, L-02, S-07, S-08). Since the mockup above was first shown, H-02 and L-01 both closed (PRs #224, #223) — the examples use that current state, not the state the mockup was approved against.
  • Not verified: how many of the 94 done items would, under this proposal's migration (P-05), turn out to have been closed with real work still open in a part nobody tracked. That is measured when P-05 runs, not guessed here.

The naming standard

The sponsor's own example, standardized: a part is <ITEM>.<LETTER> — W-10.A, W-10.B … Letters run in order and are never reused, even if a part is dropped.

  • A part is a sub-ticket: its own status, owner, share of the item, an optional waiting-until date, an optional risk word with a reason, and its own log.
  • Closing every part closes the item. There is no separate "mark the item done" step.
  • An item with no parts behaves as one part worth 100% — nothing above changes for the 94 items that will never need a letter.

Options

A · Completion view replaces Lanes

Lanes' code (share, the 80% cut, risk-tail sort) is removed from the rendered page. Ledger fields it reads (value, points, impact, likelihood) stay — proposal 25/26 still use them for routing and sizing, just not for what the sponsor looks at.

B · Completion view is added, Lanes kept as "advanced"

Same new view on top, but the old share/cumulative table stays reachable behind a collapsed section for whoever still wants the routing math. Costs one more thing to keep in sync on every render.

Recommended: B — nothing in the ask says delete the routing math, only that it should not be the thing the sponsor reads; keeping it as a folded "advanced" section costs one render branch and answers D5 without deciding it in either direction now.

Decisions

Each numbered line is one thing the sponsor answers. Keep the numbers stable once shown: answers and ledger items cite them.

  1. D1. Keep the 80% line for the finish-now/back-burner cut? Recommended: yes — it is the number the sponsor gave ("if anything is above 80%…"); changing it now would be a second undiscussed decision riding on this one.
  2. D2. Who sets a part's share of the item — recommended: the lead, when splitting the work (a judgment call about what fraction of the feature each piece is, made once, at split time) — or the blind sizer agent from proposal 25 (Z-05), which sizes items, not parts, and was never built for a share that must sum to 100 across siblings?
  3. D3. What makes a part high risk — recommended: a lead's call with a one-line reason, shown on hover — or the existing restricted paths (money, user data, secrets, releases, every common-rules change)? The existing paths mark this whole project "restricted" by declaration (risk_always), which would make every part here high risk and defeat the point of showing risk at all.
  4. D4. Should done features show by default? Recommended: no — off by default behind "show finished", per the ask ("not completely overpopulated"); 94 of 99 items today are done, and showing them by default is most of what made Lanes unreadable.
  5. D5. Keep the old share/cumulative Lanes view as a hidden "advanced" section, or drop it? Recommended: keep it, folded — see option B above.
