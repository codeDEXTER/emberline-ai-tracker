Five things the Tower should know, and doesn't

Every one of these was found by using the screen for a day rather than by thinking about dashboards. Two are trust bugs, one is a question nothing else in the estate can answer, and two are signals that have quietly stopped meaning anything.

Ordered by whether it changes what you do

Nothing here needs a new record file. Everything is derivable from git, the transcripts, gh, and bin/spend — which matters, because proposal 08's logbook was proposed and rejected, and the right response to that is to stop asking for new bookkeeping rather than to ask again.

1 · The Tower cannot tell you it is stale trust bug

Finding 1

Tower.app is a wrapper that runs bin/tower from a pinned checkout, refreshed only by build_towerapp.sh --install. Measured today, two hours after I rebuilt it:

commit
app is running208c7892 hours ago
main is atcd19f1074 minutes ago

It went stale again within the hour, and it will go stale on every merge. Before that rebuild it had been two days behind, serving the pre-proposal-09 screen — the truncated names, the 310px void, all of it — while every session reported those problems fixed.

This is the worst class of defect a status screen can have: it is confidently wrong, and nothing on it hints that it might be. Everything else in this proposal is an improvement; this one is a correction.

UI A line in the header, beside the rules stamp. Silent when current; when behind, it names the gap and what to do — running 208c789 · main is 1 ahead · restart to update. Amber, not red: it is stale, not broken.

Four million tokens across eight tasks, and none of it reaches the Tower. Look at how spend labels those rows — adoring-euler-ba942f, compassionate-bassi-fd5327. That is exactly the branch-name noise proposal 10 removed from the screen, which is precisely why cost has never been useful: cost per worktree is trivia.

Cost per feature is a different object. “Milestone 0 has cost 1.5M tokens and is not done” is a decision input — it is the only number that tells you whether to keep going, cut scope, or change approach. Once #65's register maps issues to features, the same mapping turns spend's per-task figures into per-feature ones.

UI A cost column in the LEDGER tab (#71), beside completion. Nothing on the BOARD — a card is a glance and a number invites arithmetic. One estate total in the ledger header beside the completion figure.

3 · A warning that never resolves is wallpaper signal decay

Finding 3

The header has read 5 behind: finance-tracker, idea-lab, mac-explorer +2 for this entire session — through a dozen merges, four proposals and six issues. It never changed, so it stopped being read. Measured against rules version 114:

Eleven versions is not the same fact as two, and the screen renders them identically. A permanent warning at constant volume is indistinguishable from decoration.

UI The header keeps the count, but it ages: a project more than N versions or N days behind graduates into the NEEDS YOU band as a row of its own, with the distance named. Below the threshold it stays a quiet header count. The point is that the signal has to be able to escalate, or it will be tuned out again within a week.

4 · The decision queue is under-reported the autopilot's real blocking state

Finding 4

Three PRs are open on the sponsor right now — and one of them, #62, came from a session that is not the one writing this. NEEDS YOU surfaces an open PR only when it belongs to a worktree with a mapped issue, so anything opened from a branch without one is invisible.

“How many decisions are waiting, and how long has the oldest waited” is the single number that says whether the autopilot can keep running without you. It is not on the screen at all.

UI A count in the NEEDS YOU header — NEEDS YOU · 4 · oldest waiting 4h — derived from open non-draft PRs across every project rather than from worktree mapping. The age is the part that matters: four things waiting ten minutes is a working autopilot, four waiting two days is a stalled one.

AGENT-LOG.md carries merge=ours in .gitattributes — confirmed in both pockets and finance-tracker. A file with a merge driver cannot produce a conflict: that is the entire purpose of the derecord work in #44, #45 and #57. So three of the five warnings are false by construction, not by bad luck.

The contested check is bin/whoelse's logic, and it predates the merge drivers. It has simply never been told they exist.

UI No new UI — a filter. Contested detection reads .gitattributes and ignores any path whose merge driver resolves it. On today's tree that removes three of five amber warnings. What remains says which file and why it matters, because a warning that survives the filter deserves the space.

Where it all lands

Header carries the two facts that were missing — is this screen current, and how much of the product is done. The band gains the decision queue, escalated rules drift, and only the contested pairs that can actually conflict.

Cost lands only on the ledger, beside completion. Nothing on the board: a card is a glance, and a number there invites arithmetic instead.

What I would resist

  • More regions. 900px is already tight and #70 is about to take PIPELINE's space. Everything above lands in the header, the band, or the ledger — nothing here asks for a sixth region.
  • A forecast. Cost and drift both invite “at this rate…”. Proposal 08 refused an ETA on four days of data and #63 held the same line on six. Nothing here projects.
  • New bookkeeping. Every figure above is derivable today. The logbook was rejected once; the answer is to stop asking, not to ask again.
