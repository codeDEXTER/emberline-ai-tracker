Three ways to show the features

#65 put the right information on the screen. The layout it landed in is the one the old regions left behind, and with real data in it that layout is now working against the content. Three structurally different answers, not three skins.

What the live screen is doing wrong

Measured on the running Tower after #65, at 1280×900:

  • The noise outweighs the signal five to one. Five lines say “no features declared”; one project has actual features. The projects with nothing to report are visually louder than the one with something.
  • Every feature title truncates. “Milestone 0: prove the…”, “Capture a document an…”. The region sits in the narrower grid column (2fr of 3fr+2fr) despite being the spine of the screen.
  • Blocked features render an empty bar, which reads as 0% — the exact lie the whole proposal exists to avoid. A blocked feature has no percentage; it should not have a bar at all.
  • The whole-product figure is still nowhere, and it is the thing that was asked for by name.
  • The strip's grouping is invisible — all 11 sessions fall into one “no declared feature” group, so the feature grouping cannot be seen working until registers land.

Option A · The Ledger features are the unit; projects are a column

Option A

One list of every feature, everywhere

Every declared feature across the whole estate in one full-width table, ordered by state — in flight first, then next, blocked, later. The project becomes a column rather than a section heading. Projects with no register collapse into a single muted footer line.

for Answers “what features are done” in one glance, across everything. Full width means titles never truncate. Undeclared projects shrink from five loud lines to one quiet one. Blocked features say “no percentage while blocked” instead of drawing an empty bar.

against Loses the project as a frame — when four registers land, finance-tracker's nine features will drown pockets' seven, and there is no per-project sense of “how is that app doing”.

Option B · The Board state is the unit

Option B

Columns by state, features as cards

Four columns — IN FLIGHT, NEXT, BLOCKED, DONE — with each feature a card carrying its project tag. The screen becomes a product board rather than a report.

for “What is running” and “what is done” are answered by position, before reading a word. Blocked work is visibly parked rather than pretending to be 0%. The empty DONE column is itself an honest, uncomfortable signal.

against No natural home for a completion percentage — the thing you asked for by name. Column heights will be wildly uneven (today: 1, 0, 5, 0), and on a fixed-height screen four columns of one card each wastes the space #56 fought for.

Option C · The Portfolio project is the unit

Option C

One line per project, features as segments

Each project is a single row: a stacked bar whose segments are its features, coloured by state, with the whole-product figure above. A project expands to its feature list on demand. Undeclared projects are one muted line each, in a group at the bottom.

for Puts the whole-product figure first and largest, which is what you actually asked for. Scales: twenty projects is twenty lines. The segmented bar shows the shape of a project — five blocked segments reads as “stuck” instantly, which no percentage conveys. Undeclared projects are grouped and quiet, but the group header names the gap plainly.

against Individual feature titles need an expand. Least useful of the three while only one register exists — its strength is comparison across projects, and there is nothing yet to compare.

Decision sponsor · A and B, 2026-08-07

Chosen: A and B. Not C.

aashish chose the Ledger and the Board. Recorded plainly: I had recommended C first with A later, and had argued against building B at all. That was advice on a screen he owns, he has read the argument, and the call is his — the reasoning above is left unedited so the disagreement stays on the record rather than being tidied away.

Taking A and B leaves two things unresolved that the options paper did not have to answer. Both are settled here rather than left to discover during the build.

Where the completion figure lives

The objection to B was that it has no home for a whole-product percentage — and that percentage is the thing that was asked for by name. Taking A alongside it resolves the objection rather than overriding it: A's header carries the figure, exactly as its mockup already shows (14% of declared scope, with the count of projects it excludes). B does not need one and will not have a misleading one bolted on.

How two views of the same thing share one screen

They do not, and should not try — the screen is 900px and already holds four regions. So:

  • B, the Board, is the region on the main screen. It is the glanceable one: “what is running, what is done” answered by position before a word is read, which is the job the main screen exists to do.
  • A, the Ledger, becomes its own route — /features — reached from the board's header. Full width, no truncation, room for every feature across every project, and no fight with the no-scroll budget #56 established.

This is consistent with what the Tower already is: a served document with /pulse and /session/<id> beside it. A dedicated page for the full ledger is the same move, and it means A gets better as registers land without ever making the main screen taller.

What lands regardless of which option

  • A blocked feature gets no bar — it says “no percentage while blocked”. An empty track reads as 0%, which is the lie the whole proposal exists to avoid.
  • The features region moves to the wider grid column; it is the spine and it currently sits in the 2fr of a 3fr/2fr split, which is why every title truncates.
  • Projects with no register collapse to one grouped statement, not five row-level apologies.

All three assume the fixes that are not layout choices and should happen regardless: blocked features get no bar, the region moves to the wider column, and the whole-product figure appears somewhere. Whichever you pick, those land with it.
