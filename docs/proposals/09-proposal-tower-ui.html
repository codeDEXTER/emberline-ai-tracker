The Tower, made legible

The Tower is drawing the right data. It is drawing it as one hand-positioned SVG, and that single decision is the cause of nearly everything that looks wrong on it — the truncated names, the dead space, the 23 identical circles, the 2,241-pixel page in a 900-pixel window.

The short version

The collectors (bin/tower lines 60–780) are the hard, good part and I am not proposing to touch them. Everything I want to change lives in the ~450 lines of render_* functions below them, which lay out an SVG by computing absolute x/y in Python and returning a running bottom to stack the next region on. That technique cannot wrap text, cannot reflow, and cannot let two columns agree on a height — so it truncates, voids, and overflows instead. I propose moving the page to HTML/CSS and keeping SVG only where something is genuinely drawn, then re-cutting what the screen shows so the two things that need you are not the same size as the twenty-one that don't.

What I looked at measured, not eyeballed

I ran tower --port 8893 against your live tree, loaded it in a browser and read the rendered DOM back out. Numbers below are from that run (2026-08-07 15:18, 23 worktrees, 6 projects), not from reading the source.

Findings

1. The screen does not fit its own window

The rendered SVG is 1200 × 2241. The Mac wrapper opens at 1280 × 900 (tools/tower_window/towerwin.swift:168). You see about 40% of the Tower at a time and scroll for the rest. For a document that would be a non-issue; for a glanceable autopilot screen it is the whole problem. The regions you scroll past — the session grid — are the least informative, and the ones you scroll to — progress, handovers, ticker — are the most.

2. A 310-pixel void down the left column

Node circles run from cy=190 to cy=780 (bottom edge 805). The column divider and the next section boundary run to y=1116. The gap is empty black. Cause is render_page:

main_bottom = max(graph_bottom, pipe_bottom) — two columns are laid out independently and then the page is padded to the taller one. The pipeline column is ~310px taller today, so the graph column gets 310px of nothing. Add a worktree and the void moves; add a queued issue and it grows.

3. The "live graph" is not a graph

23 nodes on a fixed 4-column grid. Position is enumeration order — row and column carry no meaning. Size is constant (r=25). Fill is constant. There are no edges except one. So the region spends 615 vertical pixels to communicate exactly what a 23-line list would, and it reads as a graph, which invites you to look for structure that isn't there.

4. Labels overflow their nodes, and truncate mid-word

Worktree names are cut at [:11], which on your tree produces arm-f-filin, arm-f-queri, arm-b-contr, arm-a-condu, backend-arc, m0-stage2-v — six names cut to something that isn't a word and isn't unique-looking. Issue titles render at font-size 10 across a circle of radius 25, so "Nothing in the app…" visibly overruns its own ring.

Hard character caps appear at [:11] [:20] [:28] [:30] [:34] [:44] [:90] [:110]. They exist because SVG <text> has no wrapping and no overflow handling — the only fit strategy available to the current design is to cut. The pipeline's top row reads "finance #81 zero logging calls in 12,679 lin": cut at character 44, one character short of "lines".

5. The signal is drowned by uniform styling

Of 23 nodes, two carry state: one purple ("needs you"), one green (active). Twenty-one identical grey circles have the same size, weight and prominence as the two that require you. The pipeline repeats the pattern: the header says IN FLIGHT · 19, but 18 of those rows are worktree-name · N ahead — a git ahead-count, not work in flight — and they are styled almost identically to the one row that is a real mapped issue.

6. The contested edge crosses the whole grid

The one drawn edge is M554,308 Q474,524 394,780 — a 470px dashed diagonal from a row-1 node to a row-6 node, sweeping across the label space of everything between. Its caption is placed at the curve's midpoint, which lands in empty grid, attached to neither end.

7. Duplicate rows presented as distinct events

Handovers rows 1 and 2 carry identical summary text. The event ticker shows four consecutive rows with the same body ("## 2026-08-03 (continued) — v4: redesign personalId…") from four different agent logs, timestamped 15:10–15:11. Four lines of a nine-line ticker are one event. Nothing here is a rendering bug — it is a missing de-duplication step before rendering.

8. Four hardcoded columns of eye travel in the work packages

render_burnup pins label at x0, bar at x0+210, percentage at bar+bar_w+20, note at +60. On the pockets row the eye travels roughly 700px from the app name to "5 / 14 items · 3 packages", across a bar, with no rule or tint connecting them.

9. No responsiveness, and inconsistent rhythm

WIDTH = 1200 is a Python constant. At a 985px browser width the page does not reflow — it clips. Vertical gaps are set by hand and disagree: 40px below the header rule, 20px below every other one. cell_h = 118, y0 = 116, +30, +10 are magic numbers with no single source.

The root cause one decision, most of the symptoms

Every render_* function has the signature (data, x0, y0, width) → (svg_string, bottom_y). The page calls them in order and threads bottom forward. This is a manual layout engine, and it is missing the three things a layout engine gives you for free:

  • Text measurement — so every string is cut at a guessed character count instead of fitted or wrapped.
  • Intrinsic sizing — so two columns can't agree on a height, hence the void.
  • Reflow — so the width is a constant and the page can only ever be 1200px.

Browsers ship that engine. The Tower is already served as HTML into a WebKit view; it is opting out of CSS and re-implementing a worse version in Python.

Do them together. B alone gives you a tidy screen that still asks you to scan 23 equal circles for the one that needs you; C alone can't be built cleanly on absolute coordinates. The collectors don't change in either, which is what keeps this a two-to-three day job rather than a rewrite.

B · the page becomes HTML

  1. One CSS grid, four regions. render_page stops threading bottom and emits a grid container. Column heights become a grid concern — the void (finding 2) cannot recur by construction.
  2. Every string renders in full or ellipsises visually. Delete all eight hardcoded [:n] caps and let CSS text-overflow and -webkit-line-clamp do it. A clamped title still ends on a word and still has a title attribute with the full text.
  3. One spacing scale. A small set of CSS custom properties (--gap-1…--gap-4) replaces +30, +10, 118, 116. Rhythm becomes consistent because there is one place to set it.
  4. Bars become CSS. render_burnup's four x-columns become a four-column grid row; the bar is a div with a percentage width. The numbers sit next to the bar, not 700px from the label.
  5. Reflow. Below ~1000px the two columns stack instead of clipping. The Mac window becomes resizable without breaking the screen.
  6. SVG stays where drawing is real — if you keep a session graph at all (see C), it is drawn, and it is the only <svg> on the page.

Not affected: collect(), every collector above it, the 5s cache, the per-region failure isolation, apprun registration, the /session/<id> and /pulse routes. The "one collector fails → that region says unavailable" contract is preserved as a per-grid-cell empty state.

C · the screen stops showing everything equally

Three cuts, in order of how much they buy:

  1. A "needs you" band, first and largest. Today the two items that require you are two circles among 23. Promote them to a full-width band at the top with the issue title, the project, and how long they have waited — and when nothing needs you, the band says so in one line and gives its height back.
  2. "In flight" means a mapped issue. The 18 worktree · N ahead rows are a different fact from the one real issue and should not share a list with it. Proposal: in-flight lists mapped issues only; unmapped ahead-of-main worktrees collapse to one line — "18 worktrees ahead of main, no mapped issue" — that expands. The count stops overstating what is in flight.
  3. The session grid is compressed. decided 615px for 23 labels with no structure was the worst trade on the page. It becomes a dense strip of state dots — one row, ~118px instead of 615px — with the worktree name and its issue on hover, and a click through to /session/<id> exactly as the nodes have today. The header carries the counts in words (23 · 1 active, 1 needs you, 21 idle), which is the only thing the grid was actually communicating.

    This retires the graph from concept 07 rather than deferring it, and that is the honest reading of the measurement: concept 07's own follow-up (message_edges(), proposal 08) found that handover edges almost never have both ends on screen, and today exactly one edge renders across 23 nodes. A graph whose edges don't exist is a grid with extra ceremony. Contested pairs — the one real edge — move up into the needs you band as a named row, which is where an actionable collision belongs anyway.
  4. De-duplicate before rendering. Collapse identical handover summaries and identical ticker bodies within a short window into one row with a ×4 count. This is a collector-side change and the only one in C that touches code above line 780.

Proposed screen · 1280×900 · fits the shipped window with no scroll · regions are CSS grid cells, not stacked coordinates · session grid compressed from 615px to 118px, "needs you" promoted from a circle to the top band

What I am not proposing

  • No change to any collector or to what is measured. Every number on the screen comes from the same place it does today.
  • No new dependency. HTML and CSS from the same stdlib http.server; no build step, no framework, no CDN — the page is served to a loopback WebKit view and must stay self-contained.
  • No change to the palette. PALETTE at line 778 is good and the screen's character comes from it.
  • No client-side interactivity beyond links. The Tower is a served document that refreshes; the disclosure triangles in the mock are <details>, which needs no JavaScript.
  • No touching pulse. The /pulse route keeps rendering exactly what it renders now.

Decisions what was open at draft, and how it closed

1. The session grid — compress, or make it a real graph? sponsor · compress

Decided by the-sponsor on 2026-08-07: compress. The graph was his concept in 07, and retiring it is his call to make, not an implementation detail. Recorded in C3 above; the ~500px it returns is what pays for the "needs you" band and the no-scroll budget.

2. Is "no scrolling" the right constraint? closed by acceptance

Yes — accepting this proposal accepts the 1280×900 budget, which is what every cut in C is measured against. If the Tower is ever wanted as a long scrolling page again, that is a new proposal, not a setting.

3. The 18 unmapped worktrees — collapse, or leave them listed? AI · collapse, not hide

Decided in-role rather than asked: per CLAUDE-workflow.md, "a question to the user is a cost" and this one is downstream of an accepted direction. They collapse into a <details> that expands in place — so IN FLIGHT · 1 stops overstating what is in flight, and nothing becomes unreachable. If watching that list for stale worktrees turns out to be a real use, it earns its own region and that is a small follow-up, not a rework.
