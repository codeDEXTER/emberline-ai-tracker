A coupling graph, read from git — what's actually tangled, not just what changed

REPORT answers "how much, how fast." It says nothing about where the risk lives — which files a change to one thing is statistically likely to drag along with it. That's a different question, and it's the one this proposal answers, for finance-tracker first.

"put in a metric pulled from git and graph analytics. basically git analytics for financial tracker."
What the data already says, before any code is written

Churn alone says these five are hot. The co-change graph says something a churn count can't: they aren't five separate hotspots, they're one. Every pair among main.py, theme.py, session.py, ledger.py and reports.py co-changes 7–15 times — a change to any one of them has, historically, come with a change to at least one other almost every time. reports.py additionally pulls in tests/test_reports.py (10) and charts.py (7). finance_tracker/money.py — the actual currency arithmetic — has been touched once in the same window: either it's stable because it's simple and correct, or it's stable because nobody has gone back to it. The graph can't tell you which; it can tell you where to ask the question.

What changes

A new COUPLING section, per project

Sits on the project page below PROGRESS, above BOARD — REPORT and PROGRESS already answer "how much, how fast"; COUPLING answers "what moves together." Same page, same live cadence, a different question.

How the graph gets built

Walk git log --name-only over the project's full history — all-time, not a rolling window, because the question is structural coupling ("do these files always move together") rather than this week's activity, and a decision already made this way. Every pair of files touched by the same commit increments a weighted edge. Two corrections against real noise found in the data pulled for this proposal: a commit touching more than ~15–20 files (a mass reformat, a checklist regeneration) is skipped outright rather than contributing n·(n-1)/2 near-meaningless edges from one event, and files that co-change with nearly everything by nature — CHANGELOG.md, CLAUDE-checklist.md, AGENT-LOG.md — are stoplisted before the walk starts.

Cutting it down to something legible

A graph of every file the repo has ever touched is not readable and not useful. Only the top ~25–30 edges by weight survive; nodes are whatever files those edges touch. That's the set the layout below actually has to draw.

The layout itself

A real node-link graph, not a table — a Fruchterman-Reingold spring embedder, hand-written in pure Python (math + random only; Tower is deliberately stdlib-only, per build_towerapp.sh's own stated philosophy, so this doesn't reach for networkx or numpy even where they happen to be on the machine). Nodes repel each other, edges pull their endpoints together with force proportional to co-change weight, positions cool and settle over a few hundred iterations, then get clamped into the SVG canvas. For ~25–30 nodes this runs in a fraction of a second — the cost here is implementation correctness (a naive spring layout can fling nodes off-canvas or collapse into an overlapping knot), not runtime.

Why it won't jitter every 10 seconds

The page auto-refreshes every 10s. A layout re-seeded from fresh randomness on every refresh would visibly rearrange itself constantly, which reads as broken rather than alive. Two fixes, both cheap: random.seed() a fixed value so identical input always produces identical output, and compute the layout inside the same cached_async TTL-bucket pattern already driving history and cost — it only recomputes when the underlying git data is actually stale, not every collect.

What this costs

  • A new TTL bucket. The git walk plus layout computation is heavier than anything on the 5s cadence — needs its own long-poll cache (GRAPH_TTL, alongside HISTORY_TTL and COST_TTL), background-refreshed, served stale while recomputing. Exact interval still open — 30–60 minutes is the range worth starting from; structural coupling doesn't move fast.
  • New render surface. Everything else on the project page is CSS grid and small SVG sparklines. This is the first hand-laid-out SVG graph Tower draws — more surface area for something to look wrong than a table would have been, which is the trade already made in choosing this over the ranked-table alternative.
  • Renames are not tracked. A file that moved shows up as two separate low-weight nodes rather than one continuous history. Worth stating rather than quietly wrong — full rename-tracking across a multi-file log walk is its own piece of work, out of scope here.

What does not change

  • REPORT and PROGRESS are untouched — this is an addition, not a reshuffle, unlike the REPORT/PROGRESS merge that just landed.
  • No new dependency. math and random only, same as everything else in bin/tower.
  • Scoped to one project at a time, same as REPORT — no cross-project coupling graph is proposed here.
Shipped with the proposed defaults, plus one found in the building

Commit-size cap landed at 18 files, top-N edges at 28, GRAPH_TTL at 40 minutes — the values proposed above, taken as confirmed rather than re-litigated. One thing the proposal didn't anticipate: the stoplist named three bookkeeping files, but building against finance-tracker's real history surfaced a bigger source of noise — several commits touch 11–13 files under docs/proposals/ at once (an index or README regenerated alongside the doc it lists), all under the 18-file cap, filling 21 of the top 28 edges with documentation cross-links and crowding out every real code coupling this graph exists to show. COUPLING_STOPLIST_DIRS excludes docs/ wholesale as a result — caught by inspecting the first real graph before wiring it into the page, not assumed correct because the code ran without error.

Build order

PhaseCovers
