How a proposal reaches you, and how you answer

In pockets you had to ask for the artifact view and the buttons every time. In finance-tracker you didn't. The difference isn't care or effort — one project has a convention for this and the other has none, so in pockets you became the convention.

The part that isn't just untidiness

Pockets' entire product direction — the rev-3 product proposal, the locked eleven-screen UI set, the v2 sync addendum — exists as three artifact links in a markdown file. One of them has a local copy. The other two don't. If an artifact is deleted or a link rots, the thinking behind this app is gone, and the repo will not notice.

So the bad experience you felt was the visible symptom of that. With no convention, delivery had to be negotiated each time; and negotiating it each time is what made it feel like work.

The proposalfour rules, every adopting project
R1A proposal is delivered as a rendered HTML artifact — never as chat prose.

Not "here's a summary, want me to write it up?" The document is the delivery. You should be reading the thing you're deciding on, not a description of it.

R2The committed copy exists before the artifact is shown.

docs/proposals/NN-<type>-<topic>.html, in the project's repo. The artifact is the view; the repo is the record. This is the rule pockets is missing, and R1 without it just makes prettier things that still vanish.

R3Delivery is immediately followed by a decision prompt with buttons.

Never "let me know what you think". The session that shows you a proposal asks the question in the same breath, with the options as buttons you can press.

R4One decision per prompt, in sequence.

Your existing preference, made general: a proposal with four open questions asks four times, not once with everything bundled. A bundled question gets a bundled answer, and the detail you actually meant is lost.

R1 and R2 are what finance-tracker already does — this writes it down so pockets and every later project inherit it instead of rediscovering it. R3 and R4 are new as rules, though they're what you've been asking for by hand.

What the buttons saya fixed set, so they aren't invented each time

Vague options are how a decision prompt becomes another round of conversation. The default set, for a proposal awaiting a verdict:

ButtonWhat it meansWhat happens next
AcceptThe direction is right Status → accepted; draft issue written; session offered; requirements and design begin
RejectNot doing this Status → rejected, with your reason recorded in the document
AmendRight idea, wrong specifics You say what changes; the same proposal is revised — not a second one
Show me firstYou want to look before deciding The demo, with click-by-click navigation, on the clean copy

Recommendation goes first in the list, per the existing convention. "Show me first" is the demo rule already in the shared file — this just makes it a button instead of something you have to think to ask for.

What it costsstated, not buried

Every proposal becomes a file, a render, and a prompt. For a two-paragraph idea that is heavier than the idea. Two things keep that honest:

  • Not everything is a proposal. Findings, gate results and status updates have their own rules and are not covered here. This applies to work that needs a decision from you.
  • The research/proposal ceremony tier already exists — nothing merges from it, so the weight is one document and one question, not a pipeline.
What this does not fix

It is a convention, not a mechanism. Nothing in the tooling forces a session to render an artifact or ask with buttons — the same honest gap as apprun start depending on an agent calling it. What changed today is that rulecheck makes "I didn't know this rule existed" checkable, which is the nearest thing to enforcement a written rule gets.

Backfill pockets, or start from now? Its three artifact proposals could be pulled down into docs/proposals/ and numbered, or left as links with the convention applying only to new work. Backfilling is the only thing that protects what's already there.

Decided2026-08-04 · aashish

Accepted. The four rules apply to every project referencing the shared rules. The three open questions above were answered in the same sitting:

QuestionDecision
Backfill pockets? All three. The product proposal, the eleven-screen UI set and the v2 sync addendum come down into pockets/docs/proposals/, numbered, with statuses.
Reports and findings too? Artifact yes, buttons no. Only work that wants a decision ends with a prompt, which is what keeps the buttons meaningful.
Buttons on a proposal with nothing to decide? Always — even when the only option is "noted". Overrides the recommendation here: there should never be ambiguity about whether a question is being asked.

Conclusions above this line are unchanged from what was accepted. Per the proposal framework, a status moves and decisions get recorded; the argument does not get rewritten after the fact.
