Milestones and proposals, on the Tower — and a smaller screen doing it

BOARD says what a project is made of. REPORT says how much is done. Neither says in what order, or where the decisions behind any of it actually live. Two new sections answer that, reusing tables and metadata three other tools already validate — nothing here invents a second convention.

Handed over, at the sponsor's request, once every supporting piece existed: "1. The Tower keeps track of every project's milestone plan. 2. Per project, he can also view the list of proposals and decision articles. 3. He suggested the Tower 'can be made simpler' while doing this."
What already existed to build on, not re-implement

A ## Milestones table convention landed in CLAUDE-workflow.md the same day (rule #109), validated by bin/milestonecheck (#112) — structure only: a Proves and a You-get column, every row fills both, states from the register's own vocabulary. bin/proposalcheck already reads a proposal's <meta name="proposal-*"> fields and the lead/section distinction (#111). Tower's job was never to parse anything new — it was to put what these checkers already validate on the one screen that shows a project's whole picture.

What changes

MILESTONES, directly under REPORT

REPORT and PROGRESS answer how much, how fast; MILESTONES answers in what order, and when there's something to hold — milestonecheck's own words for "the question that decides what to do next." Not grouped by state the way BOARD is: a milestone plan's whole point is its order, so grouping it into columns would erase the one thing it exists to show. Real data, finance-tracker, origin/main:

The column that had to be found by header, not position

The 2026-08-20 handover named this exact trap: milestonecheck originally read State from cells[-1], which broke the moment the table's optional Track column sat to its right. Not hypothetical — finance-tracker's real table on origin/main carries Track between You get and State, and the local working checkout used to write this proposal's first draft did not have that column yet (a plain, unrelated case of the checkout-lags-origin/main problem #91 already fixed for the feature register). milestonecheck itself was fixed the same way in the same PR (#114) that added Track support — it now looks State up by header, falling back to cells[-1] only when no State column is declared at all. parse_milestones() follows the same rule, so the two checkers cannot drift back apart.

PROPOSALS, at the foot of the page

Every project's docs/proposals/*.html, a lead's title and status with its part-of sections nested underneath — reference material, so it sits last, after SESSIONS, not competing with what needs attention now.

No one title convention — measured across five projects, found four shapes

The first version of the title-cleaning regex assumed "<project> · <headline> — Proposal", common-rules' own convention. Running it live against every adopting project surfaced three more, each different: "NN · status · headline" (finance-tracker, mac-explorer), plain "project · headline" with no chrome at all (pip), and "project · Proposal NN — headline" (pockets). A regex tuned to one project's convention silently mangled the other four. The fix generalizes instead of special-casing each shape: split on the last · and keep that segment — the headline is always last, whatever comes before it — then strip only the two chrome patterns that are actually generic (a leading "Proposal NN —", a trailing "— Proposal NN"). Verified against all five projects' real files afterward, not assumed correct from the one project it was written against.

The simplification: PROPOSALS is capped, same shape as QUEUED already uses

finance-tracker alone has 38 proposal documents. Every one of them on a project page at once is the opposite of what the page is for — measured directly: it rendered as a scroll of 38 rows before this was capped. render_proposals now shows the most recent 8 leads and states the rest as a count ("+16 more, older"), the exact pattern QUEUED already established for exactly this problem (#82) — extending an existing convention rather than inventing a second one, which is the "simpler" half of the brief this proposal answers most directly. The bigger simplification question — whether BOARD and MILESTONES should merge, since both now carry the same state vocabulary over overlapping rows — is named here rather than decided: it changes what BOARD means, and that is the sponsor's call, per CLAUDE-workflow.md, not a side effect of adding a screen.

What this costs

  • Zero new fetches. Milestones parse from the same register_source() text the feature register already reads (one git show, not two); proposals are local file reads, no git or gh call at all — both run in the synchronous collect path, no new cache bucket.
  • Two more sections on an already-long page. The project page now carries REPORT, MILESTONES, PROGRESS, COUPLING, BOARD, FLOW, SESSIONS, PROPOSALS — eight regions. PROPOSALS' cap is the one concrete simplification landed here; whether more should merge is named above, not decided.

What does not change

  • REPORT, PROGRESS, COUPLING, BOARD, FLOW, SESSIONS — untouched.
  • milestonecheck and proposalcheck stay the validators; Tower only reads what they already require to exist.

Added mid-build: a picture, not just a list

The sponsor pointed at the pocket-internet exploration's own milestone timeline (idea-lab/ideas/pocket-internet/09-timeline.html) and asked for that visual language reused. Two ideas carry across cleanly into Tower's own screen; the rest is that page's editorial serif design, which would clash with every other region on the same screen. Ported: a single horizontal arc — one dot per milestone, state-coloured, a diamond wherever the milestone actually hands something over, "you are here" at the first in-flight step — and a four-card meter (proven / in flight / in your hands / next you get), styled like REPORT's own card grid rather than invented fresh. Left behind on purpose: the source page's client-side lens buttons and per-row expand/collapse. That state lives in the DOM, and Tower re-requests its own page every 10 seconds — the exact failure mode that already killed a different piece of client-side toggle state once, which is why ?project= is carried in the URL instead of a :checked radio to begin with (proposal 13). Both new functions — render_milestone_arc, render_milestone_meter — are static per collect, no listeners, no toggles.

Built directly, verified against real data before wiring in

Both parsers were run against every adopting project's real files before either was wired into render_project — the Track-column case and the four title conventions were both found this way, not assumed correct because the code ran without error. test_tower_render stayed green throughout (99/99).
