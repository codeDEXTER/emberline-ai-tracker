Parallel sessions that don't collide

You asked how to stop parallel sessions reaching different conclusions and conflicting later. I went to look at what's actually on disk first. It is worse than the question implies, and it changes the answer: the problem isn't only that sessions disagree — it's that none of them can see each other at all.

The collision is already built, it just hasn't landed

Four sessions have four different uncommitted rewrites of ledger.py. Whichever merges first wins; the second hits a conflict; the third and fourth hit a file they no longer recognise. Nobody has done anything wrong — the worktree rule worked exactly as designed and kept them from overwriting each other live. It was never designed to stop them diverging.

This is not new. It has already happened twice at the rules level: two sessions independently created LESSONS.md in incompatible formats, and a second session's PR added an approval checkpoint that contradicted a decision you had already made. That one was caught only because rule changes go through a pull request — nothing else would have shown it.

Why it happensfour distinct causes, not one
  • Nobody looks. There is no step anywhere in the workflow that asks "who else is working here?" A session enters its worktree and starts.
  • Intent is invisible. Even looking, a branch name says claude/happy-benz-46db8a. Nothing says "I am rewriting the ledger's health strip."
  • Uncommitted work is invisible to git. Every one of those 43 files is unreachable by any branch-based check. The work is real and the repo says nothing exists.
  • Conclusions diverge before files do. Two sessions can decide opposite things about the same screen days before either edits it. By the time it shows up as a conflict, both have built on the decision.

The last one is the hard half and the one you actually named. A file-level check cannot catch it. What can is refusing to let two tasks own the same surface at once — which is the workflow change in R5.

The proposalfive rules · two need building
R1Look before you start.

Before the first edit, a session checks who else is in this project: other sessions, live or paused, and which worktrees hold uncommitted changes to the files this task will touch. Cheap, and derived from ground truth rather than a registry that can rot.

needs a tool bin/whoelse
R2Overlap is a stop, not a warning.

If another session holds files this task needs, do not proceed. Report it and let the user sequence the work. Exactly the principle already in force for running apps: a port in your range you didn't start is a collision to report, not to reclaim.

rule only
R3Inform the other session — don't duplicate its work.

Your ask, and the mechanism already exists: a session can send a message directly to another, which arrives there as a labelled turn with a link back. Say what this task needs, what overlaps, and ask them to commit or hand over. You see both sides.

already available send_message
R4Commit, or it doesn't exist.

A session that pauses commits work-in-progress to its branch first — even broken, even mid-thought, marked WIP. Right now 43 files of real work are one rm -rf from gone and invisible to every check in the system. A WIP commit also makes intent legible: the diff says what the branch is doing when the branch name can't.

rule only
R5Parallelism is granted per surface, not per issue.

The workflow change. You pick issues; the system should tell you when the ones you picked collide. Four issues touching ledger.py were never four parallel tasks — they were one queue nobody drew. Before a batch of sessions is opened, the surfaces are compared and contested ones are sequenced. Independent issues still run fully in parallel; that is the point of keeping this per-surface rather than throttling everything.

Why this is cheaper than it sounds

Three of the four capabilities already exist and cost nothing to use. Nobody has ever run them. This proposal is mostly a rule that says look, plus one small script that looks in all three places at once — not a new coordination system.

What it costs, and what it won't fixstated, not buried
  • R2 will sometimes block work you wanted done. That is the trade: a blocked task you can sequence beats two divergent rewrites you discover at merge. But it will feel slower on the days nothing would have collided.
  • R5 needs you at issue-picking time, which is a step you don't do today. It is a minute of sequencing to avoid an afternoon of conflict resolution — but it is a minute.
  • None of it forces anything. Same honest gap as apprun start and rulecheck: a session that doesn't run the check proceeds blind. A SessionStart hook would close it, same as for rulecheck.
  • It cannot detect divergent conclusions that haven't touched a file yet — only the surfaces they will land on. R5 is a structural guard, not a mind-reader.
Separately, and urgently

Whatever you decide here, the 43 uncommitted files are a live risk right now. They are not protected by anything, and the sessions holding them are mostly stopped. Committing each worktree's work to its own branch — WIP, no review, no merge — costs minutes and is reversible. I have not touched any of them: that work belongs to those sessions, and taking it over from here is the same mistake this proposal exists to prevent.

Open questionsyours
Should overlap block, or just warn? R2 as written stops the session. The softer version reports and proceeds, which is less annoying and much less effective.
Who sends the message — the session, or you? R3 could be automatic on overlap, or something the session proposes and you approve. Automatic is faster; approved means you always know what was said in your name.
Does R5 apply to the whole batch, or per session? Comparing surfaces before opening a batch of sessions is the strong version. The weak one checks only at the moment each session starts, by which time you've already picked.
