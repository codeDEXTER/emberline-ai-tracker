Warm-up

A cold chat becomes a lead in one command. The PhotoVault engine session already works the way every project should — plan as data, ledger updated on every change, agents tiered by complexity, rules learned the hard way written down. This proposal lifts what it did into one standard, one set of templates, and one /warmup that loads it all before the first question.

evidence PhotoVault engine, 6–13 Sepsessions read 2 · 160 sponsor turns · 3,321 tool callsdecisions asked 11

What the engine session proved

Two sessions, 6–13 September, the second running six days across six context compactions. The measured shape:

126sponsor turns in the long session
185agents spawned, 98 with a [tier · model] tag
66 / 37messages sent to / received from the app session
58ledger commits in one day (13 Sep)

What worked

  • The handoff. HANDOFF.md — 201 lines, prohibitions verbatim, standing rulings marked VERIFIED or [INFERRED], state as measured with the command that measured it. The 7 Sep session was spawning gate agents 90 minutes after "start".
  • The plan is data. Proposal 71 is a JSON ledger: 39 items, each with class, tier, model, tag, owned files, red-first test, done-when, dependencies, a log array and an issue number. The HTML is rendered from it.
  • Complexity decides the model. C1 haiku · C2 sonnet · C3 opus · C4 lead. Every agent named [ruflo · high · opus] R-01 …. The tag is the ledger row's first column.
  • Rules with dates and causes. OPERATING-RULES.md, 398 lines, each rule carrying the day and the incident. Stale-base incidents went 3 → 0 in one day once "fast-forward first" was written.
  • A lead prompt that does not stop. 72 lines: read these seven files in this order, Ruflo or halt, spawn every unblocked C1/C2 in one message, checkpoint before you stop, four sponsor-owned blockers and no others.
  • Continuous merge. His ruling of 9 Sep after seven commits piled behind one gate.

What did not

  • Status was pulled, not pushed. "Update the plan and show the burn down" ×6, "What is the current status?" ×5. The ledger now updates on every state change — that rule arrived on 13 Sep, day eight.
  • Sponsor asks fell out of the chat. On 9 Sep he asked five things in one morning. Two became issues. Three — a HEIC sidecar for analytics, an early pass to filter images, "will a rerun be faster?" — exist nowhere: no issue, no ledger row, no word "research" in the tracker.
  • Ruflo cost and did not return. Its own ledger, 27 agents without vs 43 with: tokens unchanged at every tier, memory never a usable hit, daemon auto-started and had to be stopped, npx pin drifted. "No measurable difference… a small measurable cost."
  • Briefs named a model and forgot the scope. An E2-01 agent launched the real Photos app; agents swept other agents' files into commits four times (W10-8, W11-6, W16-1, W18-B). Each was a missing MUST NOT, not a wrong model.
  • Six compactions. Each summary is a paraphrase; the session later quoted paraphrase as his words (the provenance audit exists because of it).
  • Nothing of this is shared. Every rule above lives in one repo. pockets, finance-tracker and mac-explorer each start cold.

A · /warmup — a skill, plus a check

A Claude Code skill shipped from common-rules and installed into every focus project by derecord, so "warm up" is the same word everywhere. It does not explain the rules; it loads them, in a fixed order, and ends with a state card instead of a question.

01
Read, in order: HANDOFF.md → docs/OPERATING-RULES.md → the plan of record's .json ledger → the latest docs/handovers/*-checkpoint.md → the shared CLAUDE-workflow.md. Nothing else before the card.
02
Verify, not assume: Ruflo tools exposed or not; git rev-parse --show-toplevel is a worktree or the main checkout; the test command land would run; rulecheck exit code.
03
Print the warm card: the two prohibitions verbatim · ledger count done / in progress / blocked / not started · the next unblocked items with their [tier · model] · open asks · what only the sponsor can decide.
04
Start. Spawn every unblocked C1/C2 item in one message; take the first C3 yourself. The card is the first message he reads; the second is work.

Re-warm: the same command in a running session

The field's finding is that cold starts are the smaller problem — a long session rots as its context fills with stale state. So /warmup is idempotent: run mid-session it re-reads the same chain, compares against the card it printed last, and prints only the delta — ledger rows that moved, rules added since, asks opened or answered, how far the checkpoint has drifted from HEAD, and its own token cost. Three triggers: you type it; the lead runs it after every context compaction (a SessionStart hook fires with source: compact); and every N merges, so a six-day session like the engine's re-reads its own rules six times instead of once on 7 September.

Reheat: moving a running session onto the new rules

A session running today — the engine's, the app's, a pockets chat — does not need to be restarted to adopt this. Its rules live on disk and CLAUDE.md is reloaded every turn; what it holds in its window is state, not law. So /warmup --migrate, run inside the running session (or sent to it with send_message, the way the engine and app sessions already talk):

01
Seed and convert. derecord lays down the six files where missing. An existing plan is imported into the ledger shape — proposal 71's JSON already fits; a milestone plan in HTML (pockets, finance-tracker) becomes rows through bin/tracker import, one per milestone item, class unassigned until the lead sets it.
02
Supersede, never scrap. Every old rule the new standard replaces is moved to a "superseded" block in OPERATING-RULES.md with the date and what replaced it — your rule that old content stays, marked. The session reads the new rule and can see why the old one is gone.
03
Rewrite the pointers. CLAUDE.md gets the standard's read order and "the ledger is the record"; the project's old plan-of-record pointer is replaced. From the next turn the reloaded file is what the session obeys.
04
Re-warm and diff. The card prints as usual, plus a superseded list — the rules the session was following that no longer hold — and the ledger log records migrated to standard 19 at <commit>. What the window still remembers of the old way is answered by that list every time it surfaces.

What it cannot do is erase the window: a session that has argued from an old rule for six days may reach for it again. The superseded list is the correction, on the card, until the next compaction takes the old context with it.

bin/warmup --check is the same thing as a gate: it exits 1 when a focus project lacks any of the standard files, and land consumes it — the same shape as rulecheck, proposalcheck, milestonecheck.

D · The ask ledger — nothing he says falls out

His words: "I have to sometimes give it some input about research and all, but then that does not get cataloged in the tracker." Measured on 9 September:

TimeWhat he saidWhere it went
06:18"commands should have progress bars… funny text animations"#203, #207

13:02"if I want to rerun the analysis, will it be faster?"answered in chat, unrecorded
18:38"one person might look different over the years… a mechanism to say these are the same"#225, #227

The pattern: an ask that sounds like work gets an issue; an ask that sounds like a thought gets a reply. Both are input. The rule:

Every sponsor message that is not an answer to a question becomes an ask row, in the same turn.

  "asks": [{
    "id":     "A-07",                     ← its own sequence, never reused
    "at":     "2026-09-09T12:43:00+02:00",
    "kind":   "research",                 ← research · feature · defect · decision · question
    "quote":  "Would it make sense to have a high quality JPEG sidecar for HEIC for analytics",
    "became": null,                       ← an item id (E2-09), an issue (#231), or a proposal (72)
    "state":  "open"                      ← open · answered · became-item · declined (with why)
  }]

Research asks get a research kind and a [low · haiku] or [medium · sonnet] agent by default — they are reading, not writing — and their report lands in docs/research/ with the ask id in its name. The warm card prints every open ask, so a new session cannot lose one. New task naming: an accepted ask becomes an item in the phase it belongs to and takes that phase's next number; the ask row points at it. No new letters are invented for asks.

E · The brief: tier, effort and scope — not just a model name

His note today: "it defines different models like Opus, Haiku and Sonnet, but it forgets the scope of it… we can also use a low, medium or high model." The engine's briefs are good on MUST/MUST NOT — and every incident in the right-hand column above was still a scope hole, not a model choice. So the class decides three things, and the brief carries all three explicitly:

ClassTierModel todayEffortScope it may takeTypical
C1lowhaikulowone owned file, fully specified, no design choicerename, doc sync, a comment fix
C2mediumsonnetmediumone or two owned files and their tests, a clear speca bounded fix, tests for a spec, research reading
C3highopushighcross-module; anything the drive or catalogue records; loses data if wronga schema change, a write path
C4leadthe lead's—merging, reconciling, the real library, a sponsor decisionnever delegated

The tag stays [ruflo · high · opus]: the tier is the durable word, the model is today's mapping of it. When the mapping changes (a new Haiku, a cheaper Sonnet) the ledger does not have to be rewritten — and the agent definitions in common-rules/agents/*.md carry effort: in their frontmatter so tier and effort travel together.

[ruflo · medium · sonnet] E1-10 flutter-read locations          ← name = tag + id + title

OWNS      photo_vault/flutter_contract.py, tests/test_flutter_contract.py
MUST      red-first test named in the ledger; commit by pathspec; report what you could not verify
MUST NOT  touch cli.py or db.py (lead-only); open Photos; run the full suite; git stash / amend / reset
OUTPUT    branch + commit hash · tests run with counts · red-first evidence · defects seen and left alone
EFFORT    medium — do not redesign; if the spec is wrong, record it under proposed_changes and stop

Five headings, always in this order, so a missing one is visible. OWNS lists the tests with the code (the W-flag incident). OUTPUT is the report shape the lead re-verifies against; no self-certification.

F · Ruflo, measured

The engine kept an honest ledger because he asked it to "track if it makes a difference". The verdict after 70 agents: rework fell to near zero — in wave 3, from the fast-forward and no-stash rules, before Ruflo was switched on. Tokens did not move at any tier. Its memory never returned a usable hit. Cost: a daemon to stop after nearly every agent, a drifting npx pin, MCP tools registered but not exposed in the lead session (it fell back to the CLI).

This proposal does not decide Ruflo; it puts the decision in front of him with the numbers (D3). Whichever way, the standard keeps the ledger's execution.ruflo_route field and the ruflo/no-ruflo tag, so the measurement continues wherever it is on.

G · How the lead talks while it works

Two habits of the engine session he wants kept, named so every project gets them:

A steps list before a task starts

When a new item begins, the lead writes the steps first — a short numbered list, the ledger item id on top — and then works down it. Steps are ticked as they complete, in place. The list is the item's log in draft: what did not get ticked is what the checkpoint reports.

Short, repeated status while running or waiting

While agents run, or while the lead waits on him, one line every few minutes in a fixed shape: done / in progress / blocked / not started · what just changed · what it is waiting for · what he owes it. Never a paragraph. The same line is what /warmup prints and what the checkpoint opens with, so the vocabulary is one.

E1-10 flutter-read locations
  [x] 1  memory search + hooks route, issue #253 opened
  [x] 2  agent spawned [ruflo · medium · sonnet], worktree p71/e1-10
  [ ] 3  verify in clean worktree at HEAD
  [ ] 4  ff-merge, ledger row → done, render

26 done / 3 in progress / 1 blocked / 9 not started · E1-09 merged 17:32 · waiting: R-03, R-04 reports · yours: E0-03 go

Goes into the lead-prompt template (§7 "How you report") and the warm card, so it is loaded, not remembered.

I · GitHub issues — the ledger's public face, not a second tracker

The engine already does most of this: every proposal 71 item has an issue number, the lead opens each as gh issue create "<ID> <title>" --label proposal-71, and land's Closes #N trailer closes it on merge (240 closed, 18 open). What it lacks is a rule for which side is the truth when they disagree — and today nothing checks that they agree.

Ledger (JSON in git)GitHub issue
Holdsclass, tier, model, owned files, red-first test, done-when, dependencies, log, asksthe conversation: comments, the sponsor's answers, links to PRs, the close
Source of truth forplan, status, ordernothing — it mirrors the row
Written bythe lead, by pathspec, same turnbin/tracker sync: create on in progress, label, close on done
Read back—bin/tracker render shows drift: an issue closed while its row is open, or a row done while its issue is open
Labels—proposal 18's three axes + proposal:NN; the class as tier:high

Why not the other way round: gh truncates at 30 rows and says nothing; an issue has no class, no dependencies, no log; CI is offline here, so nothing on GitHub can gate. The ledger gates, GitHub records. Asks become issues only when they become items — an open ask is a row on the warm card, not an issue nobody triages. Cross-session requests (the app session's G0–G12) arrive as issues labelled from:app and are folded into the ledger as items or declined with a comment, so the other session sees the answer where it asked.

J · Research is a lane, and it feeds the plan

Your ruling of 29 August in finance-tracker: everything goes in the milestone plan, research too, in its own lane. The engine kept research beside the ledger, not in it — docs/research/ holds five reports and proposal 71 has no research row, which is why the 9 Sep asks had nowhere to land. The lifecycle:

  • A research row is an ordinary item in a lane named for it (X-nn here; the plan's own letter), class C2 by default — reading, not writing — with OWNS the report only and a fixed report shape: question, findings with sources, options, recommendation, what only you can decide.
  • Its done-when is an outcome, not a document. The row is done only when one of three things is recorded: new items (each with discovered_from), a new numbered proposal (when it changes scope or needs your answer — the proposal's accepted items come back as rows tagged proposal:NN), or a decline with the reason. A report nobody acted on stays in progress on the warm card.
  • The tracker shows the lane with the same bars as the build lanes, so "what is being looked into" is visible beside "what is being built".
  • Any agent can propose research. A finding mid-task that needs looking into is a proposed_changes entry the lead turns into an X row — the engine already records these (20 on 13 Sep); today they wait for the sponsor instead of becoming work.

K · Surviving a compaction

The engine session was compacted six times. Each summary is a paraphrase written by the model, and the provenance audit found ten paraphrases later quoted as your words. A compaction can only lose what lived nowhere but the chat, so the defence is not a better summary — it is that nothing important lives only in the chat.

Before the cut

  • Written same-turn, never later. Every decision, ask, state change and ruling is in the ledger, SPONSOR-CONSTRAINTS.md or an issue in the turn it happened (D4, D9). If it is on disk, the summary cannot lose it.
  • PreCompact hook writes the checkpoint (D8) — current item, its ticked steps, blockers, open asks, the exact next action — before the summary is made, from the ledger, not from memory.
  • The pointers live in CLAUDE.md, which the harness reloads after every compaction: the two prohibitions, "read HANDOFF → RULES → ledger → checkpoint", and "the summary is a paraphrase; the ledger is the record". The rule that says where the truth is survives because it is not in the window.

After the cut

  • Re-warm fires automatically (SessionStart, source: compact) and re-reads the chain from disk. The card it prints is the record; the summary is context.
  • Verbatim comes from disk. A ruling is quoted from SPONSOR-CONSTRAINTS.md or the issue, never from the summary — the memory rule "summaries are not citations", made a step.
  • The diff is logged. Where the summary and the disk disagree, the lead records the correction in the ledger log (compaction: summary said X, ledger says Y). Six compactions in one session is a measurement of what summaries get wrong, not a cost to be absorbed.

Covered by D8, which grows to "the hooks on both sides of a compaction"; no new decision.

L · Memory — what Ruflo promised, from what already works

Ruflo's memory was searched by 43 agents and returned nothing usable (§F). Meanwhile three memories already work here and none of them is searched: Claude Code's own auto-memory (one fact per file under ~/.claude/projects/<project>/memory/, an index the harness loads every session — this proposal was written with it), LESSONS.md (1,618 lines in the engine, dated, with the attempt that failed), and OPERATING-RULES.md. They are memory in git. What is missing is not a database; it is recall.

Ruflo memoryProposed
Storevector DB in .swarm/, main checkout only, untrackedthe files above, in git, plus the ledger's log
Writememory store after a task; daemon auto-startsbin/remember writes one fact file in the standard shape, linked to the ledger id and issue; the Stop hook (D8) runs it for the session's LESSONS entries
Readmemory search: 0 usable hits in 43 triesbin/recall <words>: grep across every project's memory dir, LESSONS, OPERATING-RULES and ledger logs under ~/apps; each hit prints its path and date
Before a taskthe agent is told to search; finds nothing/warmup runs recall for the next items' titles and prints the hits on the card; a brief carries the hits under CONTEXT
Cross-projectnoneyes — "never git stash across worktrees" was learned in the engine and is unknown to pockets today

Grep is not a vector search, and that is the point: the corpus is a few thousand lines of prose written to be found, not millions of embeddings. If recall ever misses because of wording rather than absence, that is the day to measure a vector index against it — with the effect ledger's own method.

Six additions, folded in

  • Freshness, not presence (→ A). Each file in the chain carries its commit; the warm card prints "checkpoint 40 commits behind HEAD" instead of trusting that the file exists. A stale link is flagged, never faked.
  • The write side (→ A, new D8). A Stop/PreCompact hook writes the checkpoint and refreshes the ledger count automatically. "A session that ends without a checkpoint has failed" stops depending on the session remembering.
  • The warm-up prints its own cost (→ A). Tokens read by /warmup on the card, beside the project's context budget, so bloat is visible the day it starts.
  • Typed edges (→ B). Items carry depends already; add discovered_from so work an agent uncovered mid-task is a row with a parent, not a note in a report.
  • Escalate one tier, logged (→ E). An agent that finds its item above its class stops, records escalate: C2→C3 in the row's log, and the lead re-spawns. Cheaper than guessing the class right every time.
  • A machine-readable last line (→ E). Every report ends HANDOFF: status=… commit=… needs=…, so the gate and the next brief parse it without re-reading prose.

Not taken: making an ask structurally blocking (it would fight "do not stop"; the card and the gate are enough), and moving the operating rules into a tool-agnostic AGENTS.md (only Claude runs here today; noted for later).

Decisions

Eight. Answer in one line each, the way proposal 54 was answered (D1 accept, with a note where you want one); the answers are recorded here and in CHANGELOG.

D1The warm-up is a skill (/warmup) plus bin/warmup --check consumed by land?
Recommend accept. A skill is one word he types — cold, or mid-session to refresh, where it prints only what changed; the check is what makes a project that lacks the files fail loudly rather than start cold.
D2Templates live in common-rules/templates/ and derecord seeds the six files into a project that lacks them?
Recommend accept. Seed, never overwrite: an existing HANDOFF.md is the project's, and only its missing sections are proposed.
D3Ruflo: (a) mandatory everywhere, (b) opt-in per project recorded in the ledger, (c) off, tag kept for a later matched test?
Recommend (b). The engine's own measurement found no difference at any tier and a small cost; mac-explorer's ruling of 13 Sep stands where he made it. (b) keeps both without arguing either.
D4The ask ledger rule — every non-answer sponsor message becomes an A-nn row in the same turn, printed by the warm card while open?
Recommend accept. Three of five asks on 9 Sep vanished. The row costs one JSON object; a lost research direction costs the morning he spent forming it.
D5Briefs carry five fixed headings — OWNS · MUST · MUST NOT · OUTPUT · EFFORT — and the tag keeps tier as the durable word, model as today's mapping?
Recommend accept. This is his note of today, made checkable: bin/tracker check can refuse an agent log entry whose brief lacks a heading.
D6Pilot order: PhotoVault engine first (already 5 of 6 files), then pockets (13 accepted proposals, 0 completed), then finance-tracker, then mac-explorer?
Recommend accept. The engine costs almost nothing and proves the renderer against a real ledger; pockets is where the tracker gap is largest.
D7The steps list at task start and the one-line repeated status become part of the lead-prompt template and the warm card?
Recommend accept. Both exist in the engine session by habit; a template makes them survive the next cold start.
D8A Stop/PreCompact hook writes the checkpoint and ledger count automatically, and /warmup flags any file in its chain that is stale against HEAD?
Recommend accept. It closes the loop the field found weakest: handoffs rot when writing them is a memory task. From the research pass, not the engine session.
D9GitHub issues mirror the ledger one way — bin/tracker sync opens on in-progress, closes on done, and the render shows any drift between the two?
Recommend accept. It keeps what already works (issues, labels, land's Closes trailer) and removes the one thing that does not: two trackers that can disagree in silence.
D10Research is a lane in the ledger: an X row per question, done only when it becomes items, a proposal, or a recorded decline?
Recommend accept. It is your 29 August ruling applied to the tracker; the engine's five research reports and twenty proposed changes would all have been rows.
D11Memory is recall over what is already written — bin/recall across every project's memory, LESSONS, rules and ledger logs, run by /warmup and put into every brief — with bin/remember as the write side?
Recommend accept. It delivers the step Ruflo's loop promised (search before, store after) from three stores that already exist and were never searched. A vector index is measured against it later, if grep ever misses on wording.
