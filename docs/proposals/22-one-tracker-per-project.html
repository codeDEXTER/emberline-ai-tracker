22 · accepted · One tracker per project

Proposal 22 · accepted 2026-09-14. The sponsor asked for a tracker he can read at a glance — filters across the top, work shown as blocks — and for one tracker per project, with a proposal getting its own only when he asks. Today every proposal renders and publishes its own page, so a project with four proposals has four trackers.

The ask

Can we make the tracker a little bit visually readable with some filters or something like that? Like, a top level, uh, you know, where it filters everything, and I can see things in block, maybe visually appealing a little bit? Also, per project, there should be one tracker unless and until specified for a proposal if I need another tracker. The sponsor, 2026-09-14 19:44 (+02:00), in the common-rules lead session; recorded as ask A-01 in docs/proposals/22-one-tracker-per-project.json.

What was found

  • tracker render writes one page per ledger, docs/proposals/tracker/<stem>.html: a status line, one table per phase, asks and classes. There are no filters, and every item is a table row.
  • Pages per project on 2026-09-14: common-rules 3 ledgers (19, 20, 21) and now 22; PhotoVault engine 3; PhotoVault app 2, and the app publishes its own generated page through the declared plan_page. Each of the three projects has one publish record.
  • common-rules alone has three published tracker artifacts, one each for proposals 19, 20 and 21. The engine also keeps a hand-mirrored tracker artifact (32e06e90) beside its rendered one.
  • Five places assume one page per ledger: derecord's pre-commit hook, warmup's chain and its publish line, conformance items 2 and 10, new-proposal, and the /warmup skill's republish steps. Changing the rule is a Standard change every project has to implement.
  • Not verified: how the page reads on a phone. The artifact is checked at desktop width in both themes.

Options

A · restyle each proposal's page

Add filters and blocks to the existing per-ledger page. Cheap, and nothing else changes, but a project keeps one tracker per proposal, which is the second half of the ask.

B · one project page, rendered from every ledger

A new tracker board renders all of a project's ledgers into one page with the filters and blocks. The chain, the card, conformance and publishing move to that page; a per-proposal page is rendered only for a ledger the sponsor marked as needing its own.

Recommended: B — it is the only option that gives one tracker per project, and the filter bar is what makes one page for many proposals readable.

Decisions

Each numbered line is one thing the sponsor answers. The numbers are stable: ledger items cite them.

  1. D1. Does each project have one tracker page, covering every proposal in it?
  2. D2. Does a proposal get a tracker of its own only when the sponsor asks for one, recorded in that proposal's ledger in his words?
  3. D3. Does the page open with filters across the top and show the work as blocks, with a list view for detail?
  4. D4. What happens to the per-proposal tracker artifacts already published (common-rules 19, 20 and 21)?
  5. D5. Does a project that declares its own generated plan page (the PhotoVault app) keep publishing that page as its tracker?

Decided

D1 to D3 were decided by the sponsor on 2026-09-14, in his words above (ask A-01). D4 and D5 are the lead's defaults, and the sponsor can overrule either.

  1. D1 accepted. One page per project: T-01 builds it, and T-02 moves the chain onto it.
  2. D2 accepted. A ledger carries a tracker key (own, by, at, quote) only when the sponsor asks. Only that ledger also gets its own page (T-02, T-03).
  3. D3 accepted. A filter bar (search, proposal, status, owner, tier), one summary block per proposal, a board of item blocks by status and a list view (T-01). The look is shown to the sponsor before T-02 starts.
  4. D4, lead default. The old artifacts are no longer republished. Deleting them is the sponsor's call, because a deleted link stops working for everyone who has it.
  5. D5, lead default. Yes. A declared plan_page stays that project's published page, and the project page is still rendered and checked beside it (T-03).
