The Tower reports the product, not the plumbing

Three of the four things you asked for are straightforward and mostly involve deleting. The fourth — the degree of completion of the whole product — cannot be computed honestly today, and the reason is not the Tower.

“What features are done, what is the degree of completion of the whole product, and what things are running. I don't want to know what internal communication is going on or what branch names they are naming. That's not my problem.”
The short version

Features are already a first-class idea in your own rules — “the user owns features, the AI owns issues” — and pockets already declares seven of them in a proper register with states. The Tower simply never reads it. It reads issue title prefixes and ## headings instead, which in three of four projects are priority buckets like “Now” and “Later”. That is why the screen talks like a filing system.

The blocker: only pockets has declared what its features are. finance-tracker, pip and mac-explorer have not. So “degree of completion of the whole product” has no honest denominator, and I am not going to invent one — that is the same lie proposal 08 refused when it insisted a project with no checklist reads “no declared scope”, never 0%.

What I propose to build

1. The Tower reads the Features register, not title prefixes

pockets' shape becomes the contract: a ## Features table of sponsor-owned features, each with a state and a linked issue. The Tower reads that. compute_hulls() and its title-prefix guessing are deleted — it is currently dead code anyway, collected on every pass and rendered nowhere.

2. A session says what feature it is on. Never a branch name.

Today a session is labelled by its worktree directory. Instead: the feature it belongs to, then the issue title. Where an issue maps to no feature, the screen says unmapped work and counts it — an honest gap is more useful than a directory name dressed up as information. No branch or worktree name appears anywhere on the screen, including in hovers.

3. Handovers and the commit ticker go

Handovers are two AI sessions coordinating. The ticker is commit subjects. Both are plumbing. Deleting them also returns roughly 640px, which is most of why the pipeline currently has room for four rows.

4. Progress is measured, and movement is called out

“Highlight when progress is made” needs history, and proposal 08's logbook — the obvious way to get it — was proposed and not accepted. It is not needed: the history already exists and nobody is reading it.

  • Feature and item completion over time from git log of each CLAUDE-checklist.md: the tick count at any past commit is recoverable, so “+3 items since yesterday” is a measurement, not a guess.
  • Features closed from the GitHub issues the register links to, with their real close timestamps.

So a MOVED TODAY region can say pockets · Milestone 0 — classifier · 7/12 → 9/12 rather than listing commits. No new file, no standing obligation on any session, nothing to remember to write.

What this needs from you the part that is not code

The honest blocker

“Degree of completion of the whole product” is a fraction. Today the denominator exists for one of four active projects. I can build every region above, and for finance-tracker, pip and mac-explorer the FEATURES region will say “no features declared” — correct, and not what you asked to see.

Making it answer properly means those three projects each declaring their features, the way pockets already has. That is a sponsor act, not an AI one: your own rules say creating, scoping and closing a feature is reserved to you. I can draft candidate feature lists from what is already in each checklist for you to correct — that is the cheap version — but I should not invent the product's shape and then report progress against my own invention.
