18 · accepted · One standard across every project

Eight projects, five of them adopting the shared rules. Milestone planning is already standard and works. What is not standard is everything around it: only one project has CI, two are running rules that are 56 and 80 versions old, and there is no durable cross-project status — the only one that exists is a live loopback screen that vanishes when you close it.

Milestone planning is already the success story — leave it alone. All five adopters carry a ## Milestones table, a ## Features table and a generated docs/milestones.html. That is genuine cross-project standardisation and it did not need proposing; it needs protecting.

The drift is the real problem. mac-explorer is 56 versions behind and pip is 80. Every rule landed in the last three weeks — the test requirement, the GitHub rules, the proposal numbering, the milestone gates — is simply not in effect in two of the five adopting projects. bin/land refuses a stale project, so those two cannot land at all until someone realigns them; they have gone quiet rather than complained.

What is missingthree gaps, in cost order
What I proposesmallest first

A · Realign the two stale projects, and make drift loud

Run rulecheck --align on mac-explorer and pip, reading the changelog between their version and current so nothing lands as a surprise. Then make the drift visible rather than silent: today a project 80 versions behind looks identical to a current one until someone tries to land.

The cheap version: the Tower already reads every project — give it a rules version column, red when behind. The thorough version: a weekly check that opens an issue in any project more than N versions behind.

B · CI in every adopting project

derecord already installs the enforceable half of the rules into a project. It should install the workflow too — one file, running that project's own test command, on push and pull request. That makes CI part of adoption rather than something each project remembers.

Caveat worth stating: pockets is Swift with six packages, so its command is not the shared Python one. derecord would need to detect the project type — which bin/land's test_cmd() already does and could be reused.

C · One weekly status, generated, per project and across all

Not a new screen. A generated document — the thing the Tower cannot be, because it vanishes when the window closes:

bin/status --week            # every project, one page
bin/status --week <project>  # just one

Built only from what already exists and is already measured: milestone rows moved, issues opened and closed, PRs merged, tests added, cost from spend, and red trunks. No new record file, nothing hand-written — the AGENT-LOG lesson applies, a status anyone has to remember to write is a status that will be wrong.

The honest risk on C. This project has built one reporting tool that nobody used: spend agentlog works, is tested, and has been run once in three weeks. A weekly status has exactly the same shape, and the same way of failing. It should only be built if it is generated on a schedule and delivered without being asked for — a report you have to remember to run is agentlog again.

D · A standard shape for session-to-session messages

Sessions already message each other — three times in one day recently, all useful, all ad hoc, and none recorded anywhere afterwards. Two of the three carried a diagnosis that turned out to be wrong and was only caught because the receiving session reproduced it before acting.

The proposal is a shape, not a system: what I observed · what I think it is · what I already verified · what I did not · what I need from you. Separating observed from concluded is the whole value — it is exactly the line both wrong diagnoses crossed.

What I deliberately do not propose
  • Changing milestone planning. It is the one thing already standard across all five adopters. Touching it risks the only cross-project convention that works.
  • Adopting the three unadopted projects. geospatial-analytics, activity-manager and idea-lab may be experiments that should stay light. Adoption costs a checklist, a milestone plan and a version stamp — worth it for a product, not for a sketch. That is your call, not a default.
  • A new record file of any kind. Every merge conflict on 5 August was in a record file this framework invented.

Answersrecorded 1 September 2026

D1 — Realign. mac-explorer is realigned; it is one of the four projects in focus. pip is not in focus and is left where it is.

D2 — CI: yes, but offline. GitHub Actions is billed — ai-sangam is a private repo and ran 100+ workflow runs in seven days, with ci.yml firing on both push and pull_request so every merge pays twice. The standard is local-first: the suite runs before landing, on this machine.

D3 — Status tracking: yes, and it is the real gap. Numbering and the proposed → accepted → completed lifecycle already exist and are already used. What does not happen is proposals leaving accepted: 35 accepted across three projects, 6 ever marked done. pockets has 13 accepted and zero completed, some since 4 August.

D4 — Message shape: not decided; carried forward.

D5 — No new adoptions. Focus is pockets, finance-tracker, photo-vault and mac-explorer. geospatial-analytics, activity-manager and idea-lab stay unadopted. pip drops out of focus.

Scope correction this proposal earned: section C proposed building a weekly status report. The measurement says that is the wrong build. Numbering, statuses and proposalcheck already exist — the missing piece is not a report, it is anything that moves a proposal from accepted to completed. A weekly page listing 35 accepted proposals would restate the problem rather than fix it.
