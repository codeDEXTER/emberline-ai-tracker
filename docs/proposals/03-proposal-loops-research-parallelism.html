Loops, research triggers, and where parallel is safe

Three questions. Two of them turned out to be about things the rules barely say, and the third falls out of a design decision already made — the tool grants. The short version: the workflow is documented as almost entirely one-directional, research has no trigger at all, and parallelism is already answered by who can write what.

1 · What loops backthree stated · four buried · four missing

Reading the rules for return paths rather than forward ones: only three loops are stated in CLAUDE-workflow.md. Four more live only inside agent definitions, where the project manager never reads them. Four that should exist don't.

The one that matters: every failure routes to the code engineer

The gate can send work back to exactly one place. So a gate failure that means this approach is wrong is indistinguishable, procedurally, from one that means this line is wrong — and both get handed to the person whose job is to make the code pass. The result is a wrong approach patched until it passes rather than reconsidered. Nothing in the rules gives the gate a way to say "this needs design again", let alone "this needs research again".

The second-worst is L2 escalation. Four triggers send a decision to you, and the rules never say where it goes next — back to requirements, back to the proposal as an amendment, or forward with a note. In practice that means whatever the session improvises.

2 · When research is triggeredit isn't

The entire trigger, in the workflow file:

Verbatim

"Research and design steps are optional and run only when the task needs them."

That is not a trigger, it is a hope. And the reasoning is circular elsewhere: the research/proposal tier is defined as "research agent and/or requirements engineer", while the agent's own trigger is "the research/proposal ceremony tier". Each points at the other.

We already know what happens to steps that are optional and judgment-dependent: six finance-tracker issue sessions skipped the entire agent pipeline, and the one open-ended session ran all of it. Optional means skipped under pressure, every time.

3 · Where parallel is safealready decided, never stated

This one needs no new principle. It falls straight out of the tool grants: parallelism is safe exactly where no two workers write the same artifact.

RoleWritesFan out?Why
research-agentnothingfreely Read-only. N agents on N questions cannot conflict
proposal-auditornothingfreely Read-only. Several lenses on one artifact is better, not merely safe
test-engineernothingfreely Read-only. Split by criterion
quality-managernothingfreely Read-only, though one chair should assemble the verdict
design-explorerits own concept filesfreely Distinct artifacts by construction — and divergence is the point
requirements-engineerREQUIREMENTS.mdone only Single shared artifact. May run alongside exploration, not alongside itself
design-engineerthe specone per surface Two specs for one screen is the divergence problem in miniature
code-engineershared codenever on one surface The only role that writes what others also write. This is proposal 02's whole finding

Which gives three clean statements rather than a policy:

  • Read-only roles fan out freely. Nothing they do can collide, so the only limit is cost. Several auditors with different lenses, or several testers split by criterion, are strictly better than one of each.
  • Writing roles run one per artifact. Not one per task — per artifact. Two design engineers on two unrelated screens is fine; two on one screen is the same failure as two code engineers on one file.
  • Sequence is set by dependency, not by ceremony. Design needs requirements; test needs code; the gate needs everything. But design-explorer can run alongside requirements — its own definition already says "before or alongside" — and research fans out before anything exists to depend on.

Across tasks, proposal 02 already answered it: parallel by surface, sequenced where surfaces collide. This is the same rule applied inside a task, where the "surface" is the artifact being written.

Taking a step back — there are three kinds of loop, not oneadded on review

The table above was written by walking the build pipeline looking for return paths. That is why it found what it found — and why it missed what it missed. Reviewing it, two of the four "missing" loops got proposed rules and two did not, and the two left out are the same kind as each other. That is not a coincidence, it's a blind spot:

ClassWhat it correctsWhere it terminatesState
CorrectionThe work, inside one taskAnother agent, same task mostly stated
DirectionWhat the task isYou, or an earlier role partly, and improvised
LearningThe system itselfAlways you — rules and agent definitions are yours almost entirely missing

The learning loops are the ones that compound, and they are the ones with no rules:

  • A recurring lesson means an agent's instructions are wrong. The rules say exactly this — "the signal worth watching" — and then nothing watches it. LESSONS.md is typed and append-only, so it is countable; nobody counts it. The quality manager may flag a pattern across tasks, with no threshold and no obligation.
  • Promotion, prototype → production, is a loop through the entire pipeline — tests written retroactively, requirements documented after the fact, design locked, a full gate. It is written as a checklist, so it reads as a one-way step when it is the workflow running a second time over work that skipped it.
  • The outermost loop is the one nobody drew at all: shipped software → you use it → you find something → it becomes an issue. That loop is the entire reason a clean copy must always be running, and it appears nowhere as a return path.
  • An ask that recurs becomes a rule — this one does exist, in ASKS.md. It is the only learning loop with a written trigger, which is why the gap around the others is visible at all.
The pattern behind the blind spot

Every learning loop terminates at you, because changing the rules and the agent definitions is deliberately reserved. That is right. But it means you are the only mechanism — and none of these loops has a trigger that tells you it is time to act. The system can notice it is failing the same way repeatedly and has no way to say so.

The proposalnine rules · three added on review
L1The gate can send work back to design or research, not only to code.

A gate report names where it is sending the work: code (the implementation is wrong), design (the spec is wrong or incomplete), or research (the approach is wrong). The default stays code; the point is that the other two become sayable at all.

L2An L2 escalation names its destination.

When drift or a silent decision goes to the sponsor, the return path is stated: back to requirements, back to the proposal as an amends, or forward with the decision recorded. Never left to improvisation.

L3Every loop is bounded and says what happens at the bound.

Test↔code has two rounds. Nothing else has a limit. Same shape for all of them: a stated number of returns, then it escalates. An unbounded loop between two agents burns tokens invisibly and looks like progress.

R1Research has triggers, and they are not "when the task needs it".

Four, each checkable rather than felt: no options were ever considered for a direction now being built; an assumption failed mid-task; the same lesson has recurred — the third occurrence is a research task, not a third patch; a gate returned research under L1.

P1Read-only roles fan out; writing roles run one per artifact.

Stated once, in the roles table, next to the tool grants that already imply it — so the rule and its enforcement sit in the same place.

P2The bird's-eye page draws the loops.

It currently shows a straight line, which is a picture of a workflow nobody has. A map that omits every return path is wrong in the direction that matters, because the return paths are where the work actually goes.

L4A recurring lesson is escalated, with a threshold and an owner.

Added on review. The quality manager counts LESSONS.md entries by type and area as part of the gate it already runs, and on the third occurrence of the same lesson it must say so — as a finding that an agent's instructions are wrong, not that the lesson needs restating. It cannot fix it: agent definitions are yours. But the system stops being silent about failing the same way repeatedly.

L5Promotion is a loop, and it re-enters at requirements.

Added on review. Prototype → production is the pipeline running a second time over work that skipped it — so it is drawn and described as a return path to requirements-engineer, not as a checklist appended to the end. Same roles, same gate, same L2. What makes it cheap is that the code already exists; what makes it necessary is that nothing else ever wrote down what that code was supposed to do.

L6The outermost loop is drawn: shipped → finding → issue.

Added on review. You using the clean copy and finding something is a return path into the workflow, not an external event. Drawing it is what makes the always-a-clean-copy rule make sense — it is not tidiness, it is the input to the only loop that starts with reality rather than with a plan.

What it costs, and what it won't fixstated
  • L1 lets a gate reopen design. That is expensive and occasionally right. It will sometimes be used to avoid a hard fix — which is why the gate recommends a destination and you decide, exactly as it already recommends rather than authorises a merge.
  • R1's third-recurrence trigger needs someone counting. LESSONS.md is append-only and typed, so it is countable — but nothing counts it today.
  • P1 permits fan-out; it doesn't make it happen. Cost still argues against running four auditors on a small task, and this proposal deliberately sets no fan-out defaults.
  • None of it addresses tokens. More loops and more parallel readers both cost more. AGENT-LOG.md records per-agent tokens, so the data to judge this exists — nobody has looked at it yet.
Open questionsyours
How many returns before a loop escalates? Two, matching test↔code, is the obvious default. Design and research loops are more expensive per round, which argues for one.
Should a gate be able to send work to research? Or should the strongest thing it can say be "back to design", with research reserved for you to trigger — since it reopens the direction you approved.
Is the third recurrence the right threshold? Third occurrence of a lesson triggers research. Two is jumpier and catches it earlier; four almost never fires.
