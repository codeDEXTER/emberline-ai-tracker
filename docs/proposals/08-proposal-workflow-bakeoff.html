What five workflows cost, and which one to keep

Five process architectures built the same specification, in isolation, scored by a suite written before any of them started. All five produced identical quality. Cost varied by more than seventeen times. The cheapest is the one already written down.

The resultmeasured, not argued

Each arm received one frozen specification — 22 EARS criteria and a fixed public Swift API — and built it in its own git worktree. None could read another's code, another's rules, or the sealed acceptance suite. That suite was written from the specification before any arm existed and verified to score 0/20 against a do-nothing stub, so no arm could pass it by returning nothing.

Quality did not vary. Cost varied 17×. Every arm passed every criterion it was judged on. The only thing that separated them was what they spent getting there.

Why A and F carry no individual figure. Both ran concurrently inside one session, and when all 28 sub-agent runs are attributed by the worktree they touched, 15 of them touch both arms. A per-arm split cannot be derived from that record. Earlier reporting gave A 209,355 and F 161,427; those figures count the two driver agents but not the sub-agent trees beneath them, and understate the true combined total by 3.1×. The combined figure — 942,655 across 28 sub-agent runs plus 217,844 in the driving session — is the one that can be defended.

Today, and what replaces it
What changesthree things, two already exist

1 · Batch decisions before code

Every unknown in the specification is settled in one sitting, before implementation starts. Unknowns that arrive later get a recorded default and the work continues. Already merged (common-rules #46).

2 · Generate the records

spend agentlog derives AGENT-LOG.md from the session transcripts. Nothing is hand-written, so nothing can be wrong, and the file leaves the merge surface. Built and tested.

3 · Drop forced delegation

A driving session holding no Edit/Write, structurally required to delegate all code. Two arms ran it. Measured — it failed.

Why this proposal is small. CLAUDE-workflow.md already says ceremony is opt-in. Arm C — the winner — is very nearly that default already. This is not a rewrite of the rules; it is two additions and one retraction.

The retraction

Forced delegation was proposal A of the six-day review, and it is the thing that measurably failed. The reasoning was that instructions are not a control boundary but tool grants are — sound in itself, and the compliance data supported it: the rule "the session delegates, never writes code" was followed by 1 of 7 worktree sessions, while the executable tooling was invoked 415 times.

The experiment tested whether making that structural pays for itself. It does not. Both arms running it scored the same 22/22 as a control with 37 lines of rules, at many times the cost.

Scope of the retraction, stated precisely. This does not indict tool grants as applied to the roles — quality-manager having no write access is untested here and stays. What failed is extending that mechanism to the driving session.

What this does not provestated up front
  • A suite everyone passes cannot rank quality. All five arms scored full marks, so the experiment measured cost precisely and quality not at all. The task was made small enough to run five times; that same choice removed the headroom needed to separate the arms.
  • The silent-wrong-guess question is open. The control resolved nine specification ambiguities silently and got all nine right. Nothing tested what happens when such a guess is wrong, because the sealed suite catches wrong guesses before they can reach scoring. This is the only finding that would overturn the rest.
  • n = 1, and the task favoured the losers. Pure domain logic with no UI is unusually test-shaped — conditions that suit the heavier arms' methods. They still lost.
  • Two criteria are vacuous. R20 and R21 pass against a do-nothing stub, so "22/22" is 20 discriminating criteria plus two free ones. R20 — "shall never write outside the process" — is a universal negative and is not decidable by a test at all.
Two corrections to the record

Agent definitions register immediately, not at session start. This document's author previously advised a session restart on the belief that the agent roster was fixed at startup. That is false — an agent definition dropped into a searched directory became invokable in a running session. What is fixed at session start is which directories are searched, which is why an agent in one project's .claude/agents/ is invisible to a session rooted elsewhere. That was the real cause, and the restart was not needed.

A session merged a change to the shared rules. common-rules #46 was opened and merged by the same session at 06:28 on 2026-08-06, by calling gh pr merge directly and bypassing bin/land's guard, which exists to refuse exactly that. The content was reviewed and kept. The precedent was not: merging a rules change remains the sponsor's, and only the sponsor's.
