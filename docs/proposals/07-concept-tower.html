The Tower — a live window on the autopilot

Your ask: a running app showing all the sessions, how they talk to each other, where the blocking points are, which tickets are in the pipeline — live, fed by the sessions themselves. The autopilot flies; you sit in the tower. This is the concept, with the screen drawn, the data sources verified, and a build path with honest costs.

The screenone window, four regions — drawn with today's real data
  • Live graph (left). Every session is a node — pulsing when active this minute, amber when blocked, grey when idle. Feature hulls group the tickets of one feature. Green dashed edges are real messages between sessions — verified observable in transcripts today. Amber edges are holding patterns: a contested surface, queued behind whoever holds it. Purple edges run to the wall — the only things waiting on you, with how long they've waited.
  • Pipeline (right). Tickets by state: queued per surface, in flight, at the gate, merged today — and a separate "at the wall" row that is exactly your to-do list and nothing else's.
  • The ticker (bottom). The digest, live: commits, handovers, gate verdicts, decisions taken-and-recorded. Reading it for a minute answers "how is the autopilot handling things."
  • The header. Rules version and alignment, plus the day's wall count — the autonomy metric, permanently on screen.

Why this is smaller than it looks

Every hard question is already answered by an existing tool — Tower is pulse + whoelse + apprun with a watcher loop and a browser push. Stdlib Python, no dependencies, one process. It registers itself through apprun like any other running app, gets a port and a badge, and obeys leave-nothing-running. The autopilot's window is itself flown by the autopilot's rules.

Build paththree steps, each usable on its own
Step 1 — pulse, but live.

pulse --serve: the existing page, re-rendered every 10 seconds behind a local port, auto-refreshing. An afternoon of work; you get "live" immediately while the real screen is built.

Step 2 — the Tower screen.

The window above, minus message edges: graph from transcript freshness, pipeline from issues + worktrees, ticker from git log and AGENT-LOG appends, wall items from pending questions. This is the version that answers your ask.

Step 3 — the conversation layer.

Message edges parsed from transcripts, handover provenance ("who gave what to whom, when"), and click-through: click a node, read that session's last digest; click a wall item, land in the conversation that's waiting.

Honest limits

It reads transcripts, which are private session logs — the Tower must stay a local app, never published as an artifact with real transcript content. Polling means "live within ~5 seconds", not streaming. And a wall item only disappears when you actually answer in that session — the Tower shows the queue; it cannot clear it.
