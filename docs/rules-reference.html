The shared rules, and what a new project gets

One file of rules, twelve tools, eight agent roles. A project adopts it by adding four lines to its own CLAUDE.md and running one command. This is what those rules actually say — and, more usefully, which of them are enforced by a program rather than asked for in prose.

The four that carry itmeasured, not asserted

The rules file was 1,637 lines and is now 594. The cut was made after measuring four days of real sessions. These four are what the measurement said was load-bearing:

1 · A worktree per task

Separate folder, separate branch, always.

Sessions sharing a checkout overwrite each other's work. Seven parallel sessions ran with one collision all week.

2 · Tool grants, not instructions

Only code-engineer holds Edit and Write. The other roles cannot change code.

A rule the AI cannot break needs no paragraph.

3 · A gate that reads the diff

quality-manager checks against acceptance criteria. It reports; it never fixes and never merges.

A role that can fix what it finds will stop reporting.

4 · Tests, run before landing

bin/land refuses to merge a red branch.

Green suites are not evidence unless something consults them at the moment of merge.

Enforced vs. asked forthe distinction that matters

The rules file's own opening principle: "Rules that can be enforced are not written here. A rule the AI cannot break needs no paragraph." Three weeks of measurement backed it — executable guards are used ~99% of the time; prose rules were followed 1 time in 7.

Ceremony is opt-in. The full chain runs only on work the sponsor has flagged as a feature they care about. It is not the default, and that is measured rather than preferred: five process architectures built one frozen spec, all scored identically, and cost varied 17×. The lightest arm is what the default already prescribes.

Reserved to you, always
  • Anything under common-rules/ — surface and ask, never edit unprompted
  • Merging a change to these rules — the AI opens the PR, you merge
  • Creating, picking and closing features
  • Clearing orphaned processes or archiving sessions
  • finance_data/, auth.json, .env — never leave the machine in the clear

Everything downstream — cutting issues, sequencing them, resolving disagreements between sessions, choosing between implementations — is the AI's job, done without asking. "A question to the user is a cost, not a safety move."

Adopting it in a new projecttwo steps
  1. Point at the rules from the project's own CLAUDE.md — four lines near the top. Never copy the text inline; that defeats the sharing. 
    Shared workflow rules (worktree-per-task, pre-merge gate, issue
tracking, confirmation gates): ../common-rules/CLAUDE-workflow.md —
read that first. This project's specifics: test command is <…>,
build/run is <…>, GitHub repo is <owner/repo>.
  2. Install the enforceable half, once: 
    common-rules/bin/derecord /Users/the-sponsor/apps/<project>
    That installs the .gitattributes union-merge rules, a pre-commit hook that refuses conflict markers, and a SessionStart hook running rulecheck --quiet.

Then keep only the project's own specifics in its CLAUDE.md: exact test and build commands, repo name, label taxonomy, and any gitignored files a fresh worktree needs copied in.

What the project should also have, and what happens without it: a tests/ directory (land lands "on the gate alone" without one), a ## Features table and a ## Milestones table in CLAUDE-checklist.md (land refuses without a well-formed plan), and a CI workflow running the identical test command. Currently only two of three projects have that last one — and both repos that lack it have had an unnoticed red trunk.

Honest limits
  • The prose half is weakly held. Everything marked prose above depends on judgement, and judgement measured at 1-in-7 compliance before the guards existed.
  • common-rules is exempt from its own gate. land exits 3 for it, so the repo hosting every check is the one where none apply at merge time. Its trunk is red as of this writing, for exactly that reason.
  • The eight-role org is thinning. code-engineer is now 65% of all dispatches, and both verification roles have fallen in absolute terms. The guards absorbed their job — which is arguably right, but it happened by drift.
  • One tool is dead. spend agentlog works, is tested, and has been run once in three weeks.
