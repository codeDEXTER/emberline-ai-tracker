# Adoption: what stands between the standard and running a project

> **Adopt the tag, not `main`.** As of 18 Sep 2026 the standard has a
> baseline: **`v1.0.0`**. A project catching up should target that tag, which
> does not move while it works, rather than a `main` that gains mandatory
> changes underneath it. `docs/RELEASE-1.0.0.md` says what is in it.

Written 18 Sep 2026 by the common-rules lead, after the sponsor asked to
"continue and finish so I can run the actual projects".

The honest finding: **the standard is finished and no project can run it.**
common-rules is at rules version 578 with all twelve conformance checks
holding, a 201-second merge gate and a tracker the sponsor signed off. Across
eight project repos, **not one has a ready card** — and every red card has the
same single cause, which is not a bug:

> ✗ mandatory Standard change not implemented — implement it first, then
> `rulecheck --align`

That is the standard working as designed (proposal 21, S-09). A project may
not align its stamp past a mandatory change it has not implemented, because
the stamp asserts the project follows the rules, and aligning early would make
that assertion false. The consequence is that every improvement to the
standard raises the adoption debt of every project that has not caught up.
**Four mandatory changes were added on 17–18 Sep alone** (O-02, O-03/O-07,
O-08, RF-01).

## What a project session does, in order

Run these **in the project**, not here. This lead cannot: writing into another
project is prohibited, and each project's own session owns its ledger.

1. **`/standard`** — the sponsor's own mandatory ruling. State your refactor
   stage, then work the twelve-item checklist in `skills/standard/SKILL.md`.
2. **`common-rules/bin/warmup --project . --migrate --dry-run`**
   — writes nothing and lists what it would do. Show the sponsor that list
   before running it without `--dry-run`. For a repo with no ledger this is
   the step that creates one from the plan it already has.
3. **`rulecheck --project . --mandatory`** — quotes what each pending entry
   asks for. Queue each as a ledger item owned by `lead`, ahead of other work
   (proposal 21, section 3). Implement, record the evidence, and only then
   **`rulecheck --project . --align`**, which refuses while any mandatory
   entry is still pending.
4. **`warmup --project . --check`** must read ready before new feature work
   starts, or the reason must be a `blocked` ledger row naming what is needed
   and from whom.

The catch-up queue is long but it is mostly mechanical: of the 21, most are a
declaration in `.common-rules.json`, a hook `derecord` installs, a template
regenerated, or a command swapped for the tool that replaced it. The
substantive ones are the token levers (proposal 23), the Ruflo loop (RF-01),
one tracker per project (P22 T-02/T-03) and `bin/handover --check` (P24).

## The recommendation

**Stop adding to common-rules.** The rulebook is not the bottleneck; adoption
is. Every feature added from here widens the gap for eight repos, and the
standard's own design turns that gap into a red card on the next session that
opens the project.

Take one project — `PhotoVault/app` is the shortest path — work its 16 entries
to a green card, and let what that costs tell you whether the remaining seven
want the same treatment, a shorter standard, or a slower one.
